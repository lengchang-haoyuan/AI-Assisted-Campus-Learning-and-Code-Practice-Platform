## 3 动作、等待点与完成门槛

| 动作 | 合法业务范围 | 结束行为与拒绝语义 |
| --- | --- | --- |
| `start` | understand 的 ready | 只预约一次有界指导；成功到 waiting_confirmation。重复业务键重放原操作；不同键并发开始由状态或版本拒绝 |
| `hint` | understand 的等待点；implement 无提交时保留 S07 通用模板指导；已有提交时必须选当前 attempt | 无提交的通用 hint 不读取或假装评审不存在的代码；已有提交未选 ID 为 409，选旧尝试为 409。代码提示只消费选定当前代码，保留原静态反馈 |
| `explain` | understand 的指导；implement 必须有并选定当前 attempt | implement 无提交或未选 ID 为 409；不在会话内的尝试为 404。只讲解当前代码，不代写完整答案 |
| `review` | implement 的当前代码尝试，显式传 attempt_id | understand review 为 422；无提交/未选择为 409；已有有效评审不得用新操作覆盖。无效结构或 Provider 失败进入 failed，保留错误 |
| `confirm` | understand 等待理解确认；implement 等待有效完成确认 | 理解确认只推进到 implement；实现确认必须绑定当前 attempt 与当前 revision，并满足下列全部完成条件。确认不调用模型 |
| `cancel` | 未取消、未完成会话，包括模型运行中 | 同事务保存 cancelled 与事件；正在运行的请求以 cancelled 错误终结，评审尝试转 review_failed。不能覆盖历史完成事实 |
| `resume` | cancelled 的安全等待恢复；可恢复等待点；超期残留 running 的故障恢复 | 不发模型。未到 recover_after 的 running 为 409；超期后记 recovery_timeout、转 failed，是否重试由本人决定 |
| `continue` | 存在明确失败请求的 failed 会话 | 显式重试原 request_type、effective_action 及绑定 attempt；保存 retry_of，不猜测新任务。评审重试必须仍选原失败的当前 attempt；不会借此覆盖已有有效反馈 |

implement 完成同时要求：当前尝试已有非空代码；服务端按固定 T01/T04 比较声明值均匹配；当前绑定的 `PracticeReviewResult` 为 `overall=pass` 且 C01–C06 六项均有效 pass；attempt、模板、Context 与请求引用一致；最后由已认证本人带当前 attempt 和 revision 确认。

声明值比较要求字段集合一致、类型为整数且数值相等；布尔 `true`、字符串 `"1"` 或浮点 `1.0` 不能冒充整数 `1`。只有 AI pass、只有声明匹配或只有“我已通过”的声明都不能完成。自测声明允许 false/null，独立留存，不替代实际完成门槛。

有效评审后的等待由当前尝试推导：满足完成门槛到 `waiting_confirmation`；有效评审有确定问题或声明仍不匹配到 `waiting_revision`；无评审或 `insufficient` 到 `waiting_submission`。这些等待状态均可重新查询；取消后恢复沿用同一推导，不隐式重评。

外层反馈 schema 为 `practice-feedback/1.0`，静态评审 schema 为 `practice-review/1.0`。见 [evidence.py](../../../../backend/app/practice/evidence.py) 与 [review.py](../../../../backend/app/practice/review.py)。

四类业务证据是自测声明、声明值比较、AI 静态评审、教师认可；个人确认单独记录来源和引用，不合并进教师分栏。

review 包含 summary、overall 及恰好一次的 C01–C06；每项含 criterion_id、verdict、issue_type、evidence_span、reason、suggested_self_test、next_action。fail 必须有匹配该 criterion 的问题类型、原代码中逐字存在的片段、建议自测和下一动作；unknown 必须请求缺失材料，保留不确定性。有 unknown 时 overall 必须 insufficient；全 pass 才允许整体 pass。结果中的四项身份由服务器绑定，模型不能自填身份或来源。

工程校验只证明结构、绑定和引用存在，不证明引用的语义判断正确。本轮冻结16例已实际评价：数值指标达标，但两项C04引用虽存在却不支持额外问题，故质量未通过，见[差距定位](S08-本轮质量差距定位.md)与[原规则汇总](S08-评价运行/20261022-flash-pro-r1/rule-summary.json)。

## 5 版本、幂等、历史与事务

会话创建固定白名单 Context 版本快照，后续项目 Context 更新不覆盖旧会话。所有动作核对 owner、session revision、operation、当前 attempt 及 attempt_no；模型返回后再次核对，任何身份不再匹配都只记迟到审计，不能改变当前状态或绑定反馈。

创建、提交、动作分别使用 UUID request_key：相同键且规范化载荷相同，返回已有记录；相同键但代码、声明、self_statement、版本或动作不同，返回 409。声明以规范 JSON 比较，区分 bool 与 int。重放在版本检查前定位原操作，因此客户端在网络中断后可以先 GET，再用原键查询/重放，不能换新键试探收费调用。

新提交追加 attempt_no，不提供覆盖旧提交的写接口；code、declared_output、self_statement 保持提交原文。尝试 status、错误和已绑定反馈会在受控事务中更新，不把整个数据库行称为永久不可变。新尝试移除当前 implement 的 step_outputs 引用及活动操作引用，保留 understand 和历史结果。详情中 `current_attempt`、`is_current`、`candidate_stale`、`can_confirm` 明确当前候选；旧尝试 `candidate_stale=true`、不能确认，但仍可阅读。

事务分为预约和收口两段：短事务按 `Project → PracticeSession → PracticeAttempt → Event` 相对顺序锁定，多行按 ID；提交并释放锁后才等待模型；返回时新事务重新校验并保存状态与事件。人工等待不持事务，普通 GET 不产生模型、Spark 或业务写入。已发生的供应商请求不承诺天然恰好一次；关闭自动重试，失败重试只能由 continue 明确触发。

## 6 事件与后续离线接入

事件与有效业务状态在同一事务提交；回滚不留成功事件，重放不放大事件。事件键从 request_key 及固定后缀派生；criterion 事件再追加 C01–C06，不依赖 nullable 唯一键。

| event_type | 产生位置 | 引用与边界 |
| --- | --- | --- |
| `session_created`、`session_started`、`guidance_requested` | 创建与指导预约 | 模板、步骤、版本、operation/request；不是学生已完成 |
| `attempt_submitted` | 新尝试保存 | session/attempt、attempt_no、提交版本；不含代码和声明正文 |
| `review_started` | 评审预约提交 | 当前 attempt、operation、ai_request；不代表模型已成功 |
| `review_finished`、`review_failed` | 绑定结果、失败收口或运行评审被取消/恢复失败 | 明确是哪次已绑定操作；迟到结果不伪造当前成功事件 |
| `criterion_issue`、`revision_requested` | 当前有效评审的确定问题与修订等待 | criterion_id、对应 issue_type 与 attempt 引用；未知项不编造问题 |
| `step_confirmed`、`session_completed` | 合法本人确认事务 | 理解确认为 understanding，实现确认为 practice_owner；完成另有事件 |
| `session_cancelled`、`session_resumed` | 取消或安全恢复事务 | 反映动作发生及当时版本，不自动发模型 |

事件实体含 id、session_id、可空 attempt_id、event_key、event_type、可空 criterion_id/issue_type/confirmation_kind、occurred_at、action_payload。action_payload 白名单为 request 的动作/版本/ID元数据、template_id/version、step_key、context_version、revision、operation_id、ai_request_id、status，以及有尝试时的 attempt_id/attempt_no；不存代码、评语、自测正文、声明输出、Prompt 或密钥。

S07 的历史事件覆盖起点沿用原证据。本轮S08已按具体许可在隔离MySQL生产事件：[事件样例](S08-证据/attempt-feedback-and-events-example.json)中`attempt_submitted` ID `1dd433e6-a24b-40b6-abf1-bbc5b4ad3741`时间为UTC `2026-10-22 02:43:16.356263`，模板1.0、attempt1、revision5。它是隔离Fake工程首次提交覆盖记录，不充当生产上线/自然课堂起点，不回填历史。S10只能在后续阶段按批准的source/metric新版本选取这些白名单引用，不能提前修改旧ODS、旧完成批次或现有指标。
