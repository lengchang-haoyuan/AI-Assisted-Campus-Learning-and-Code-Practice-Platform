### 2 必须保留的三处关系边界

1. **个人 daily_tasks 与教学 teaching_assignments 没有直接外键。** 项目 → 个人任务是个人学习支路；班级 → 教学任务 → 提交 → 反馈是教学支路。学生可在提交版本中引用本人项目，由用户身份和项目归属连接两条支路，不能靠同名标题连接。

3. **提交内容版本不等于不可变代码快照。** summary、repository_url/ref 和 request_payload 被保存，但未抓取仓库代码；分支／标签可能移动。状态、reviewed_at、revision 与项目引用可按既有动作变化，不能把整行称为永久不变。学习记录删除还可能使 Feedback.learning_record_id 按 SET NULL 断开，不能用残留 JSON 标记补造可信关系。

### 3 可修改性与分析限制

| 来源 | 当前可变性 | 对后续抽取和分析的影响 |
| --- | --- | --- |
| projects／learning_plans | 状态、关联、字段可按既有业务规则更新；有 created_at／updated_at | 是当前快照，不能仅凭当前进度重建历史趋势 |
| daily_tasks | 可更改日期、关联和状态或删除；完成时间随完成／状态动作处理；无完整状态事件史 | scheduled_date 是 DATE；取消仍属于现有任务总数口径；按记录快照统计，不能冒充每日历史完成率 |
| learning_records | 无 updated_at；普通记录内容、时长、发生时间和关联可修改／删除；时长 nullable | max(id) 增量会漏掉更新删除；优先窗口全量一致性快照，分开记录 NULL、0、记录数与已知分钟 |
| teaching_assignments | 发布后部分正文冻结，可延长截止等；有发布／关闭／归档时间 | 当前截止时间与 submission.assignment_due_at 保存值可能属于不同语义，S01 明确选用；无须新增全套事件系统 |
| submissions | 最新版本号、revision、updated_at 随业务动作改变 | 当前头不是提交历史；历史由 submission_versions 与 feedback 表表达 |
| submission_versions | 内容版本按追加保存；状态、评阅时间、revision、项目引用可变化 | 稳定键用 submission_id + version_number；提交时间和评阅时间可分析等待，不等于学习投入时长 |
| feedback | 每个版本最多一个反馈；learning_record_id 可因关联记录删除变 NULL | 来源需真实 ACCEPT、对应版本和学生一致，缺失关系进入质量统计 |
| workflow_runs／ai_requests | 有界运行、状态和耗时／Token 元数据；不是学生分步提交事件 | 可作既有系统运行指标；不能据此补造人工等待、修改轮次或学习掌握情况 |
| learning_reports | 成功结果是生成时事实快照，当前业务后来变化不回写旧报告 | 不能当作未来 Spark 批次表；旧事实与新增离线口径须分开 |

UTCDateTime 在数据库保存 UTC，在 Python 边界恢复时区；scheduled_date、计划起止日期和报告周期是 DATE。后续必须冻结业务时区和半开时间窗口，避免把 DATE 再按 UTC 偏移。
