## 本阶段关键设计和调用链

- 调用链：`POST /api/v1/workflows/{id}/run → WorkflowService → WorkflowEngine → WorkflowAgentRegistry → BaseAgent → ProjectContext → AIClient → AIProvider → LLM → AgentResult → ContextManager → WorkflowExecutionRepository → MySQL`。
- `requirements_analysis → tech_stack_analysis → architecture_design` 使用拓扑排序确定执行顺序。非法引用、自环、重复边、循环、条件边和未注册节点在创建 Run 前拒绝。
- 默认 `mode=incomplete` 只执行非 success 节点及其所有下游，`mode=all` 才明确重跑整图。已全部成功的图再次使用默认模式返回 409，不创建无意义重复 Run。
- 技术栈 Agent 写入 `language/framework/frontend/backend/database` 后，ContextManager 根据节点读写策略把依赖变化字段的架构节点标记 stale；当前运行继续重新生成该节点并恢复 success。
- 每个节点开始前提交 `WorkflowRun/WorkflowNode/AIRequest=running`，模型调用不包含在数据库事务中；模型结果通过对应 Pydantic Schema 后，ProjectContext、Project 核心字段、节点结果、AIRequest 和 AIResult 在独立事务中原子提交。
- 同一 Workflow 的未过期运行通过行锁拒绝；超过恢复期限的遗留运行、AIRequest 和 running 节点在下一次运行中分别恢复为 failed、failed 和 stale。
- 节点数、模型回合、顺序并发、总超时、单节点 Token 和单次 completion-token 预算均有配置上限。AIClient 只重试明确可重试且幂等的短暂 Provider 失败。
- HTTP 请求取消会取消 Provider 协程并将 Run 持久化为 cancelled、当前节点置 stale；本阶段明确不提供跨进程主动取消接口。

## 手工验收步骤和实际结果

1. 创建包含“需求分析 → 技术栈分析 → 架构设计”的 Workflow，并为 Project 保存有效 ProjectContext。
2. 使用 Fake Provider 和真实 MySQL 调用 WorkflowService。首次 Run 为 completed，3 个节点与 3 条 AIRequest/AIResult 均为 completed，架构进入 ProjectContext。
3. 将技术栈节点标记 stale 后以 `mode=incomplete` 重跑。第二次 Run 只包含技术栈与架构 2 个节点，语言由 Python 更新为 Java，后端由 FastAPI 更新为 Spring Boot；架构下游在失效后被重新生成并恢复 success。
4. 重新查询 Run 列表与详情，确认两次业务 Run 和 5 条结构化节点结果可从 MySQL 读取并再次通过 Schema。
5. 构造未过期 running 记录，重复运行被拒绝；将其时间调整为超过恢复阈值后，新运行把旧 Run/AIRequest/节点恢复为 failed/failed/stale。
6. 验收脚本按外键顺序清理临时 AIRequest、Project 和 User；清理后 `p13_verify_%` 用户数量为 0。
