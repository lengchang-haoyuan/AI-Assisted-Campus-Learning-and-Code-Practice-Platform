## 复现与最小设计

修复前节点/边 CRUD 和工作流删除没有活动运行检查；整图替换只校验图版本。节点提交只验证 Context 版本，运行结束没有验证启动时的图版本。原锁序中启动使用 Workflow → Run，节点提交使用 Run → Node → Request → Workflow → Project，与手动 Context 的 Project → Node 写入存在反向等待。

回归使用虚构的三节点 DAG、合法 Context、真实 Repository/Service/Engine、SQLite 内存表及可控 `asyncio.Event` Fake Provider。另在隔离 Python 进程加载 Git HEAD 的四个原始模块执行同一组行为测试，未回退工作区文件。

- 早期基线：9 项测试产生 18 个断言失败，包含 15 种图写入未拒绝、直接 Repository 预改对象未拒绝、节点提交及结束运行错误标记 completed。
- 最终基线：13 项测试产生 27 个断言失败；新增的无事务断言优先捕获旧实现模型等待期间仍有读事务。两次基线的断言层次不同，不能直接比较失败数量。
- 最小设计：编辑前加锁并读取当前图；Repository 写入前再次检查；所有直接相关事务采用 Project → Workflow → Run → Node → Request 顺序；启动图版本作为内部参数传至各执行提交点。

## 修改内容

1. 活动运行期间，节点和边的增删改、整图保存（含同值保存）及工作流删除返回现有 409 冲突语义；节点名称和坐标也受保护。判断依据是数据库中的 RUNNING WorkflowRun，不依赖工作流显示状态。
2. Service 在验证和修改 ORM 对象前取得锁；Repository 在 `no_autoflush` 中再次检查当前版本及活动运行，避免直接调用时提前写入脏属性。锁后用当前读取刷新图，避免 MySQL 一致性快照早于等锁过程。
3. 工作流自身 name/description 可在运行期间更新，不递增图版本；状态更新仍受活动运行保护。
4. `start_node`、`complete_node` 和 `finish_run` 都校验启动图版本。冲突时回滚本次提交，再通过原失败路径保存可重试终态，旧响应不写 Context/AIResult。启动时还核对锁后 Context 版本。
5. 执行、编辑和手动 Context 路径统一父锁顺序；恢复与失败路径不受图版本冲突阻断。启动及节点开始后的重载读事务在返回前关闭，生产会话配置下模型等待期间 `session.in_transaction()` 为 False。

## 关键设计决定

- 使用已有 Project/Workflow 行作为短事务互斥边界，适配手动 Context 的父锁顺序。项目内不同工作流的短写事务会按项目串行化；模型调用期间不持锁。
- 图版本保存在本次运行的内部参数中，不新增运行字段或持久化格式。错误 code 为 `workflow_version_conflict`，沿用现有字符串错误字段和 failed 状态语义。
- 失败、取消和超时恢复保持原有路径，避免拒绝旧结果时反而留下永久 running。
- 隔离 MySQL 验收必须得到本轮明确授权。建议新建 `scholarhub_l4_20261016_cr1`，已有同名库则拒绝；建现有模型表，只写虚构样本，结束仅清理本轮样本，保留库和表。

初次代码交付时未连接 MySQL；确认后已完成专用库补验并清理。全程未调用真实模型。验收脚本只允许固定专用库名前缀及本机连接，必须显式初始化且目标库不存在；不会读取或清空业务表，公开错误仅包含受控说明或异常类型，不输出连接凭据。
