# P19 成果提交与教师反馈实施方案

状态：2026-09-09 用户已确认 D6、API 与增量数据库方案，P19 已完成技术实施及隔离验收。技术确认不等于教师确认或校方批准。

## 1. 实际基础与范围

已核对根 README、文档索引、项目说明、前后端目录职责、AI 提示词 README、P16 方案、P17/P18 报告以及实际 Router、Model、Service、Repository、前端路由和依赖。未发现工作区 AGENTS.md，遵循会话提供的全局规则。

- P17 身份和 P18 班级、成员、教学任务已有前后端代码；复用当前身份、班级授权、分页及任务详情，不把教师姓名字符串当权限。
- 实际任务流转是 draft → published → closed → archived；发布后题意冻结，仅延长截止。以 P18 代码及 P16 后续 D5 确认为准。
- 成果提交、版本、教师反馈和业务通知均尚未实现，也没有仅完成 API 的上述模块。源码中的登录动画 feedback 不是教学反馈。
- LearningRecord 支持空时长，但现有 Service 要求 task 类型关联个人 DailyTask，且普通记录允许编辑；P16 教学事件需要专用写入和来源保护。
- P18 部分操作先锁任务再锁班级；P19 必须检查相关操作并统一锁顺序，避免与归档、成员移除互相死锁或越过授权变化。
- AI 提示词 README 顶部“P16–P24 尚未实施”、早期 P16 现状和后端目录职责中的 Redis 属于旧描述/规划，不能作为当前能力证据。P16 末尾 D1–D5 已确认，D6 未确认。

保持 Vue 3、TypeScript、Vite、Element Plus、Pinia、Axios、Vue Flow、ECharts 和 FastAPI、Pydantic、SQLAlchemy、MySQL。无新依赖、无新部署服务；保留 Provider、Agent、Workflow Engine。个人 Course、DailyTask、Project 与教学实体继续分离。

## 2. 已确认并实施的最小数据设计

推荐沿用 P16 第 5 节的四张表，不创建未来阶段模块。下列字段和约束均为拟实施，不代表已迁移。

| 实体 | 字段职责与约束 |
| --- | --- |
| Submission | id、class_id、assignment_id、student_membership_id、latest_version_number、revision、created_at/updated_at；UNIQUE(assignment_id,student_membership_id)，学生成员和任务必须同班；没有正文和重复状态 |
| SubmissionVersion | id、submission_id、version_number、request_key VARCHAR(64)、summary TEXT 1–8000 字、repository_url VARCHAR(1024) 可空、repository_ref VARCHAR(100) 可空、source_project_id/source_project_title 可空、status、submitted_at/reviewed_at、revision；UNIQUE(submission_id,version_number) 和 UNIQUE(submission_id,request_key)；正文不可更新 |
| Feedback | id、submission_id、version_number、teacher_membership_id、class_id、decision accept/return、comment TEXT 1–4000 字、created_at、learning_record_id 可空；每版本唯一终局反馈；教师成员、提交必须同班；学习记录关联唯一 |
| Notification | id、recipient_user_id、event_key VARCHAR(160)、kind assignment_published/feedback_created、assignment_id、feedback_id 可空、created_at/read_at；UNIQUE(recipient_user_id,event_key)，只存事件引用，不复制提交正文 |

所有时间使用既有 UTCDateTime，API 带时区，页面明确按 Asia/Shanghai 显示。提交、反馈外键 RESTRICT；项目来源、反馈到学习记录的外键 SET NULL。复合外键沿用 P16，需给既有任务、成员增加对应 (id,class_id) 唯一约束；Submission 增 (id,class_id) 唯一约束。最新版本指针使用两表创建后追加复合外键，初始为空、同事务补齐，不对外返回空提交。

索引沿用 P16：(student_membership_id,updated_at,id)、(status,submitted_at,id)、(teacher_membership_id,created_at,id)、(recipient_user_id,read_at,created_at,id)。版本历史分页按 version_number DESC，其他列表带 id 次排序。page 1–10000、page_size 1–100，默认 20；前端不一次加载全部版本或成员。

教师专用 DTO 只返回提交说明、仓库链接与版本标识、来源项目标题、版本状态、时间和反馈；不返回 source_project_id、Project 描述、Context、笔记或 AI 输入。来源标题由后端读取本人项目，其他正文由学生预览后提交。

## 3. D6 已确认规则与授权

| 场景 | 推荐行为 |
| --- | --- |
| 首交 | 当前有效学生、有效班级成员、active 班级、published 任务，服务端 now < due_at 才能提交；等于截止即拒绝 |
| 重交 | 只允许最新版本 returned 后追加 V+1；submitted 待评及 accepted 均禁止追加；逾期须教师先延长期限 |
| 反馈 | 当前本班有效教师仅对最新 submitted 版本提交一次 accept/return 和必填意见；旧版本或不同内容重复反馈 409 |
| 关闭 | closed 禁止学生新交/重交，仍允许有效教师处理已交待评版本；不可重新发布，退回后只能留存修改要求，不能继续提交 |
| 归档 | 班级或任务 archived 后提交、反馈只读，不自动接受待评版本 |
| 误评 | 不支持覆写意见或接受后重开；保留证据，单独确认更正方案；如必须同任务纠错，应在本次确认时提出再调整 |
| 学生退出/移除/校园资格停用 | 禁止新交、班级名册和实时任务读取；底层 User 仍有效时，可从本人历史入口读取已交快照及反馈；有效本班教师仍可评阅退出前待评版本 |
| 教师退出/停用 | 立即撤销该班阅读及评阅权，历史署名保留；User 停用对所有角色禁止认证访问 |
| 项目删除或取消共享 | 删除来源项目或主动解除来源仅置空来源 ID，标题、已交正文及反馈保留；社区取消发布不删除教学证据 |

学生之间、不同班教师之间拒绝读取提交，管理员无提交正文和反馈权限。所有对象 ID 均后端重查作用域，不靠前端隐藏。本人历史使用独立所有者查询，不借此开放已退出班级的实时任务或其他学生记录；标题与截止展示来自首次提交冻结的任务概要，拟在 Submission 增加 assignment_title、assignment_due_at 快照字段，明确标注“首次提交时”，有效成员另外查看实时截止。

仓库链接推荐仅接受 HTTPS、精确主机 github.com/gitlab.com/gitee.com、无凭据、无非默认端口、无查询参数或片段且有仓库路径；禁止 IP/本机/私网和脚本协议。用户可只交说明，不强制仓库。版本标识是学生声明，不证明仓库或代码存在。服务器不做 DNS 查询、抓取、重定向或执行；外链使用 noopener/noreferrer。自建 Git 主机暂不开放，后续按具体主机确认。

通过反馈在同事务创建本人 LearningRecord：record_type=task、task_id/course_id=NULL、duration_minutes=NULL，仅写事件和来源 ID，不修改 Project 或 DailyTask。专用内部路径不放宽普通手工 task 记录校验；通过 Feedback 关联判断系统来源，不信任客户端 metadata。普通记录接口编辑此类事件返回 409；本人删除事件仍允许，Feedback 关联置空且重试不再生成。教师不通过私人学习接口读取事件。这是明确的既有接口行为变化，等待确认。

提交/反馈教学证据留存期限、真实教师与校方政策仍待确认。开发版不自动清理教学证据或通知，不承诺永久保留；正式试点前确认期限及删除流程，P19 不提供批量删除教学证据入口。

## 4. 事务、重试与通知

统一相关操作锁顺序：班级 → 任务 → 涉及的身份/成员（稳定 ID 顺序）→ Submission → Version。锁内重查账号、校园资格、班级成员、任务状态及截止；并检查现有身份停用、成员变更路径的锁配合，不能用无锁预检查充当最终授权。

首次提交通过唯一约束与事务串行化；request_key 同键同内容返回已有版本，同键不同内容 409。先重新验证访问资格，再识别历史重放，不因提交已经接受而复制旧请求。项目来源解除后仍须能识别原请求：拟在版本内部保留规范化原请求 JSON（仅上述提交输入，不复制项目私密信息；source_project_id 为原输入值而非可导航授权），专用于比较，不对教师返回。替代方案是解除关联后旧键统一 409，推荐保留原请求以支持一致重试；这是额外持久化字段，须一并确认。

反馈锁 Submission，校验 expected_revision 和 URL 版本号。已有相同教师、同决定同意见的反馈返回原结果，其他冲突 409；先校验作用域。同事务落反馈、状态、通知及通过事件，任一步失败全部回滚。

任务发布通知在原发布事务生成，接收人仅发布时有效学生；后加入者直接看任务列表，不补历史通知。反馈通知只发提交者。固定事件键由任务/反馈 ID 生成，唯一约束去重。教师依靠待评列表，不增加学生提交通知类型。

通知列表、未读计数及已读仅按 recipient_user_id 查询。失去目标权限后仅显示通用事件和“当前无访问权限”，不泄露任务标题或反馈正文；本人历史反馈仍可跳转本人历史。默认进入页面/手动刷新获取，不增加后台轮询服务。

## 5. 页面与公共 API 草案

统一前缀 /api/v1；独立 Schema，Router → Service → Repository → Model。

| API | 约定 |
| --- | --- |
| POST /campus/assignments/{id}/submissions | request_key、expected_latest_version（首次 0）、summary、repository_url/ref、source_project_id；首次 201、同键重试 200 |
| GET /campus/assignments/{id}/submissions | 教师本班列表/学生本人，分页与状态筛选 |
| GET /campus/submissions | 学生本人历史、教师本班待评，分页；学生待办另外沿用任务列表并扩展本人提交状态筛选，包含未交任务 |
| GET /campus/submissions/{id} | 概要、最新版本；按当前身份区分本人/教师 DTO |
| GET /campus/submissions/{id}/versions | 分页版本与各自反馈，禁止无界嵌套历史 |
| POST /campus/submissions/{id}/versions/{number}/feedback | expected_revision、decision、comment；201/200；旧版本冲突 409 |
| DELETE /campus/submissions/{id}/versions/{number}/project-reference | 本人主动解除关联，204；不改正文；归档后也允许本人取消来源引用 |
| GET /notifications | 分页、未读筛选、本人 unread_count |
| POST /notifications/{id}/read | 幂等标记本人通知，跨用户 404 |

无权资源 404、身份不具备资格 403、输入不合法 422、状态/版本冲突 409，沿用现有异常结构。现有普通 API 和路由保留；扩展任务列表的提交筛选/摘要字段，不改变原默认结果。

复用 ClassroomsView/ClassroomDetailView 的任务列表显示学生未交/退回与教师待评；TeachingAssignmentDetailView 加提交预览、提交按钮及班内提交列表。增加 /campus/submissions（本人历史或教师待评）、/campus/submissions/:id、/notifications，复用 AppLayout。API 集中 src/api，类型集中 src/types；版本分页、重复提交禁用、失败保留输入、重试复用同 request_key。接受/退回/取消关联有确认文字；具备加载、空、失败、重试状态、键盘及窄屏支持，不另建工作台。

## 6. 影响、选项与推荐

| 变化 | 事实与风险 | 选项和推荐 |
| --- | --- | --- |
| 数据库 | 四张新表、既有表复合唯一约束、内部请求与任务概要快照；新增外键影响删除顺序，发布通知随班级人数增长 | 推荐 P16 增量关系表；不塞入 Project JSON，不创建消息平台 |
| API | 上述新接口及教学事件编辑保护；旧客户端对新系统事件编辑将收到 409 | 推荐保留原路由/普通记录语义，前端识别只读教学事件；不更换 API 版本 |
| 通知一致性 | 单体单库可同事务；大班发布事务可能较长 | 推荐当前一个班试点的事务内落库，内部有界分批查成员；大规模投递另行评估 |
| 教学规则 | 截止拒交、一次终局反馈可能不满足教师纠错习惯 | 推荐本方案最小闭环；若需宽限期/误评重开，先补状态和验收设计 |
| 依赖/部署 | 现有栈满足 | 不新增、不升级、不改变部署 |

确认后先备份再执行新的 P19 增量迁移；同步 Models/schema.sql，不重写已发布迁移。历史个人数据不转换、不补发旧任务通知、不自动建账号。先验证空库与 P18 升级库约束一致，再启动业务。若已有新数据，关闭写入口并前向修复；回退应用时保留增量表，不删证据。恢复备份须另行确认恢复点后的数据损失。

## 7. 确认后实施与验收

顺序：增量模型/迁移 → Repository/Service 与隔离测试 → API → 复用页面与通知 → MySQL/API/浏览器链路 → 报告及仅本节点提交推送。提交前核对已有项目说明、演示文档和日志差异，不捎带无关修改。

验收必须覆盖 V1→退回→通知→V2→通过→双方刷新保留历史；双教师双班及不同学生隔离、关联他人 Project、非法 URL、截止相等边界、同键重试和异内容冲突、并发反馈、旧版本、通知越权/去重/回滚、成员退出与停用、归档、项目删除/解除引用、教学事件编辑拒绝与删除后不再生。只用隔离虚构样本，不访问外部仓库。

确认清单中的四表及附加快照/请求字段与复合约束、API/页面、HTTPS 主机范围、关闭/截止/误评规则、无时长事件与编辑保护、增量迁移和本地隔离验证均已由用户确认并实施。教师确认、校方批准和正式留存政策仍独立待定。
