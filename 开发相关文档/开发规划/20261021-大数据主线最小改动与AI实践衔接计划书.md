“最小”按最小完整结果衡量。归属、并发版本、真实事件、失败恢复和任务原子创建是完成这条链的必要部分；减少这些内容会把问题留到 S10。模板市场、通用节点解释器、队列、实时流、学生代码沙箱和预测模型没有当前必要性。

```text

               规则候选 → 本人审阅确认 → 一次任务创建
```

S07–S09 的失败不能破坏已有分析；普通查询、刷新和切图始终不启动 Spark、模型或业务写入。

## 四 分阶段执行与验收

每次只执行一个阶段。下表中的人日是单人有效开发的粗估，前置材料可用且无重大失败时合计约 11–18 个工作日，不包含等待授权、模型失败后的新轮次或论文定稿。阶段验收优先于日历。

| 顺序 | 预计投入 | 本阶段唯一主要结果 | 进入下一阶段的条件 |
| --- | --- | --- | --- |
| S06 收口 | 0.5–1 日 | 既有专题解释的 J1 结果及完整 / 未完整结论 | 校准与正式评分满足门槛，或用户明确修改前置关系 |
| S07 | 2–3 日 | 固定模板持久会话与单步等待 | 版本、归属、并发、取消迟到、重启恢复有证据 |
| S08 | 最小适配 | 提交 / 辅助建议 / 本人审阅 / 恢复 | 新模式工程实际验收；原质量封存，不收费补考 |
| S09 | 2–3 日 | 学生端真实接入与桌面 / 手机操作 | 四类辅助路径可用，确认不伪装代码正确 |
| S10 | 2–4 日 | 新事件分析及建议只创建一次任务 | 旧批次兼容、新答案正确、应用原子且可追溯 |
| S12 / S13 | 1–3 日技术整理 | 最终版本复验、证据与论文交接 | 不再增加功能，按实际完成范围写结论 |

S11 默认跳过。以下阶段的验收不得由“预计已足够”替代。

### 1 S06 收口

**输入：** 既有完成报告、同批事实、解释文本、独立答案、[评分表](../阶段报告/AI大数据改造/V2/S01-评价评分表.md)。先检查是否已有可直接评分的独立解释稿；没有则整理现有内容，并固定具体文本与版本，不重跑 Spark 或新增来源记录。

**操作：** 准备 J1 的 G01–G03 校准材料、专题评分输入和调用账本。真实模型型号、输入许可和费用明确后才运行。若尚无有效校准，本次需要 3 次校准加 1 次专题评分；原方案总计仍为 36 次，校准在 S06 完成且配置未变时由 S08 复用，S08 后续为 16 次被测加 16 次正式裁判。角色额度不互借，失败计入消耗，不自动重试或增加总额。当前实际授权仍为 0。

**验收：** 校准 3/3；专题四维各 0–2 分，合计至少 6/8，且没有因果或能力夸大；原始响应、模型、参数、费用及引用可核对。校准失败、abstain、invalid 或评分不足都保留实际结果。

**停止：** 无真实调用授权时完成准备材料并保持“J1 待评”。按当前阶段包前置条件，不能自动进入 S07；若用户希望先做 S07 工程，须明确调整前置关系，并保留 S06 缺口，不能改写为已通过。

### 2 S07 最小持久会话

**范围：** 固定 `python-learning-csv / 1.0`，只有 understand → implement 两步；先实现创建、本人查询、单步帮助、确认理解、取消、恢复和对应事件。不做完整工作台和质量实验。

**最小设计：**

- 会话绑定 owner、项目、模板版本及 Context 白名单快照；每次动作核对 `expected_revision`。后续 ProjectContext 改变时，旧会话继续绑定原快照，界面提示旧版本；不静默换料，也不因项目当前版本改变而抹掉历史。
- 状态使用 S01 明确的 `ready / running / waiting_submission / waiting_revision / waiting_confirmation / failed / cancelled / completed`。S07 仅启用本阶段可达部分；不照搬旧 Word 泛称 `running_step / waiting_input` 再另建一套枚举。
- 短事务准备 operation 与版本 → 提交并释放锁 → 有界模型操作 → 短事务重新核对并提交结果。锁序遵守 `Project → PracticeSession → PracticeAttempt → Event`，多行按 ID；不持锁等待模型或学生。
- 重放同键同载荷返回已有结果；同键异载荷和版本冲突拒绝。网络中断先查询状态，服务重启后的遗留 running 有明确失败 / 恢复路径，恢复不自动重发收费请求。
- 真实动作成功提交时保存最小事件与稳定 event_key；回滚不留成功事件、重复动作不放大事件。此时开始记录覆盖起点，而不是等到 S10 才采集。

**验收：** Fake 状态测试与实际隔离 MySQL 证据分列；重点验证重复 / 并发开始、跨用户、错误版本、取消后迟到、模型失败、查询零调用和重启恢复。旧工作流编辑互斥、历史运行、Context 失效及 S06 批次保持可用。

**停止：** 本阶段完成报告与交接更新后停止。缺少本轮具体隔离目标和写入范围时，停在迁移文件和可审阅差异，不向业务库执行 DDL。

### 3 S08 提交恢复与AI辅助建议收口

**范围：** 复用已有提交、确切反馈、不可覆盖历史、取消与恢复。AI按需提供建议，不判代码正确或学生通过。用户已批准此定位，原自动评审质量未通过保留并停止收费重评；不再迭代评测提示追分。

**实际适配：** 当前源码仍有overall=pass等完成门槛，下一次S08应最小调整。当前attempt有有效代码、归属/版本/状态合法后，由本人审阅并结束本次实践；AI未请求或失败时可恢复到人工等待。解除模型pass、六项结论及输出匹配的自动通关依赖。输出比较、AI建议、本人确认和教师来源独立保存；completed只表示流程结束。不得执行学生代码或改变正式教学权限。

**验证：** Fake覆盖直接审阅结束、自选修改、无提交、取消恢复及建议失败、并发/重复/越权/错版本/迟到响应；按本轮隔离授权补真实数据库与重启证据。旧工程成绩不充当新模式验收。无需被测/J1新调用，原Q01–Q16、参考答案、阈值、原始结果和账本封存。

**停止：** 新模式工程适配及相关验收完成后交接S09，原AI质量不再阻挡后续工程；只更新提示词不算实现通过，不自动推进。详见[收口说明](../阶段报告/AI大数据改造/V2/S08-辅助建议收口说明.md)。

### 4 S09 项目准备和实践工作台

**范围：** `/projects/:id/ai` 维护目标、已定技术、材料及版本；新增 `/projects/:id/practice` 处理当前步骤、提交、反馈及恢复；`/workflows/:id` 保留高级画布与历史。沿用现有 Campus Studio、请求 client 和结果组件，不重做全站导航。

优先复用 [WorkflowExecutionPanel](../../frontend/src/components/WorkflowExecutionPanel.vue)、[WorkflowNodeResultContent](../../frontend/src/components/WorkflowNodeResultContent.vue) 的合适展示部分。新 criterion 反馈与旧类型不一致时增加局部适配，不把新状态强转为旧运行结果。

**验收：** 两页使用真实接口；直接审阅结束、自选修改、无提交、取消恢复均有明确下一动作；刷新 / 重新进入恢复当前版本；历史切换、长代码、快速请求、换号和晚响应不串数据。前端类型 / 构建、桌面和 390px 证据分别记录。本人确认仅表示审阅，原自动评审质量未通过只作历史限制；页面不显示代码正确或教师通过。

**停止：** 候选 Context 写回仅复用已批准的现有机制；缺少依据则只展示来源和差异。本版不因页面需要新增第七个 B 组接口。

### 5 S10 实践事件分析与一次建议应用

**范围：** 从 S07/S08 实际产生的会话、尝试、事件按白名单抽取，明确启用时间；使用 S01 规划的 source-2.0 / metric-2.0 方向，具体版本标识和字段差异在本阶段冻结。旧 source-1.0 与旧批次继续可读，禁止补造上线前事件。

新汇总首先使用既有批次专题 JSON 容器保存有界、强校验的实践摘要，不给旧 daily 表不断增加实践列。若实际所需结构超出 S01 已批准范围，先列新增差异确认，不能把 JSON 当作任意载荷通道。

源码已有两处需要在本阶段一起适配：后端 [PublicationPayload / BatchDetail](../../backend/app/schemas/analytics.py) 当前对版本与 TopicSummary 强校验；前端 [requireSupportedBatch](../../frontend/src/api/offlineAnalytics.ts) 当前只接受 1.0，列表遇到任意不支持批次会整页报错。因此必须明确识别已支持的旧版 / 新版响应并按版本读取，覆盖混合列表和旧详情；不能只放宽字符串检查而用旧 DTO 渲染新版。采用明确的两版分支即可，不建设通用版本注册平台。未知版本仍有明确不支持状态。

**唯一建议规则 B-R1（辅助语义）：** 同一会话、同一criterion，至少两个不同attempt的已绑定AI建议重复报告同issue_type且用户未处理，可提醒补一个边界自测。只说明重复建议，不确认真实代码错误；数据不足不触发，次数不推导能力。旧批次/规则保留，新版明确语义来源；建议文本优先确定模板，无需新模型。

**一次任务创建：** 候选绑定 batch/cutoff/metric/template/session/attempt/criterion；用户审阅标题、日期和本人项目后确认。服务端重新计算候选，核对当前来源与版本，使用原生候选元组和 request_key；同一事务保存任务及映射，重放返回同 task。首版 `plan_id=null`，不改已有计划任务集合。

当前 `LearningService.create_task → LearningRepository.save_task` 会自行提交，因此不能先调旧方法，再补建议映射。需按已批准设计新增窄的原子创建用例；复用输入和归属规则，保留普通创建接口。并发、故障回滚和同候选异 request_key 也必须只创建一次。用户改过新任务后，重放与原请求载荷比较，不与后来可编辑任务字段比较。

**验收：** 真实动作 → 事件 → 一致性快照 → Spark → 新批次 → 图表 → 建议 → 一次任务全链可追溯；新指标与独立答案一致；旧 1.0 样例与本人查询仍可用；越权 / 旧版本 / 失败不留半个任务。原模型质量未通过封存，不阻挡过程统计/建议应用，也不能追认为质量通过；GET仍零Spark/模型/写入。

**停止：** 完成本阶段并交 S12，默认跳过 S11。若工期不足，提交保留已有 A 主线、延后新增分析的具体缩减方案，由用户决定，不擅自宣布 B 联合闭环完成。

## 五 如何为后续改造保留空间

| 现在做的必要准备 | 后续直接获益 | 当前不额外建设 |
| --- | --- | --- |
| 固定 template_id/version、context_version、session/attempt/operation 引用 | 结果和恢复不串版本；将来模板变化可区分 | 模板市场、动态节点 DSL |

| 不改旧完成批次；新分析明确版本 | 新旧结论可并存，回归边界清楚 | 提前写未知新版字段、通用兼容框架 |
| 建议来源与任务原子映射 | 重放、故障和后续追溯有据可查 | 哈希体系、自动改计划、多规则引擎 |
| 固定评价材料与实际调用账本 | 能复验质量，防止把工程通过当模型有效 | 训练管道、多裁判、无限调参 |

这就是“最小改动且便于后续改造”的边界：把下一阶段确定依赖的信息一次记录正确，把尚未请求的能力留在以后。
