# ScholarHub 项目逻辑与代码闭环缺口清单

- 检查日期：2026-09-27
- 代码基线：`main`，`3d459ad`；检查对象包含当前工作区源码
- 文档用途：明确毕业设计原型尚未闭合的逻辑、验证和产品叙述；本清单不是修复完成报告
- 配套总方案：[毕业设计整改方案](20260927-毕业设计整改方案.md)

## 一、结论与判定范围

项目已有多个**代码层业务闭环**：教师发布教学任务、学生分版本提交、教师退回或通过、学生收到通知并查看历史；个人项目与 AI Workflow 的保存、运行、结果查询；社区作品申请、人工审核、举报和复核。这些路径不需要推倒重写。

但“所有模块都存在”不等于“项目整体已完全闭环”。本次检查发现：个人学习计划的状态与任务关系存在可到达的不一致；AI 学习报告的事实数字可能只通过格式检查；当前全链路验收脚本与校园权限规则不一致。另有统计口径、真实模型测试入口，以及社区/AI 到个人实践的人工衔接，需要修正或准确限定主张。

本清单中的“闭环”分三层：

1. **业务状态闭环**：同一使用场景中，创建、变更、反馈和再次查询的状态保持一致。
2. **实现与验证闭环**：前端、API、Service、持久化和回归样例能共同证明主线。
3. **毕业设计证据闭环**：论文、演示与实际实现一致；技术验证不冒充真实教学效果。

## 三、逐项证据、影响与验收

### L1：终态计划与新任务可能同时存在

- **代码位置**：[计划状态变更](../../backend/app/services/learning.py)、[任务创建和关联解析](../../backend/app/services/learning.py)、[计划进度重算](../../backend/app/repositories/learning.py)、[任务编辑器](../../frontend/src/components/LearningTaskEditor.vue)。计划状态由 `active` 转为 `completed` 时要求进度达到 100%，但任务关联解析只检查归属、日期和项目，没有检查计划是否已完成或已取消。前端计划下拉框也不按终态过滤。
- **可到达场景**：计划中的任务全部完成，计划改为 `completed`；随后新建一项待办任务并关联该计划。服务层最小样例确认创建路径进入保存调用。Repository 在写入后会重新计算计划进度，因此可能形成“状态已完成、进度低于 100%”。`cancelled` 计划也存在同类关联入口。
- **建议**：先定义终态计划是否冻结。推荐终态计划不可新增或改挂任务；如确需恢复计划，应另行设计明确状态转换，而不是让任务操作隐式改写终态。约束应落在服务端，前端只同步限制选项。
- **验收**：对 `completed`、`cancelled` 计划分别测试创建任务、把已有任务改挂进去、通过工作台完成相关任务；非法操作返回明确冲突且计划/任务均不变。用隔离数据库验证进度与状态仍一致。

### L2：计划元数据与已有任务可能不一致

- **代码位置**：[更新计划](../../backend/app/services/learning.py)、[创建/更新任务时的关联规则](../../backend/app/services/learning.py)、[学习计划编辑器](../../frontend/src/components/LearningPlanEditor.vue)。`update_plan` 校验新项目和课程属于本人、日期区间自身有效，然后直接保存；它没有读取已有任务。任务创建或更新时却要求任务项目与计划项目一致、任务日期落在计划范围内。
- **可到达场景**：计划关联项目 A，已有任务继承 A；之后把计划关联项目改为 B，任务仍指向 A。服务层最小样例显示计划字段可改为 B，更新过程未查询任务。缩短计划日期也可能留下计划与任务日期不一致，具体数据库结果需隔离验证。
- **建议**：在更新计划时核对已有任务。推荐先拒绝会破坏既有任务约束的变更，并给出可操作错误；若产品确需批量迁移任务，再设计原子更新及历史语义，实施前确认影响。
- **验收**：分别覆盖“已有任务时改项目、缩短日期”“没有任务时合法编辑”“任务重新关联”三类样例；提交失败后计划与任务维持原状态。

### L3：报告中的事实数值尚未形成可信闭环

- **代码位置**：[聚合源](../../backend/app/repositories/learning_report.py)、[模型输出 Schema](../../backend/app/agents/learning_report_schemas.py)、[报告生成与保存](../../backend/app/services/learning_report.py)、[页面事实卡片](../../frontend/src/views/AnalyticsView.vue)。后端计算学习分钟、活跃天数和任务完成率，再将聚合指标交给模型。模型返回的同名事实字段满足数值范围时即可保存并展示，未与本次聚合源逐项比对。
- **影响**：格式合法但数字错误的模型输出仍可成为已完成报告。现有测试验证结构有效、格式无效和敏感内容拒绝，未覆盖“结构有效但数字不一致”的样例。
- **建议**：推荐由后端填写报告中的事实数字，模型只生成分析与建议；若保持模型返回结构，则在持久化前逐项核对并拒绝偏差。涉及公开响应或持久化语义时，先确认兼容影响。
- **验收**：Fake Provider 返回正确结构但错误学习分钟或完成率时，不得保存为带错误事实的 `completed` 报告；正确样例仍可生成、查询并刷新显示。

### L4：当前版本尚缺可复现的总主线验收

- **代码位置**：[旧全链路脚本](../../backend/scripts/verify_integration.py)、[校园社区权限](../../backend/app/services/community.py)、[2026-09-25 现状报告](../阶段报告/20260925-项目全量现状与GitHub交付报告.md)。旧脚本注册普通账号后直接访问 `/community/projects`；现状报告记录 P21 权限规则下该步骤返回 403。
- **性质**：这是验收工具与当前业务前置条件不一致，不能直接认定社区功能失败；但也不能用该旧脚本证明现版“全链路通过”。
- **建议**：使用虚构账号和隔离数据库，补足校园邀请/身份、发布申请与人工审核等前置步骤；可以最小适配旧脚本，也可以提供等效、可重复执行的主线验收。不要放宽当前权限规则来换取通过。
- **验收**：从干净隔离环境走通账号、个人项目、计划/任务/记录、AI Fake Provider、社区审核、教学 V1→退回→V2→通过，并在刷新后重新查询关键结果；保留命令、版本、样本和结果。

### L5：统计百分比的分母尚未明确

- **代码位置**：[查询仅取前 `limit` 项](../../backend/app/repositories/statistics.py)、[按返回项之和计算占比](../../backend/app/services/statistics.py)、[前端技术栈图表](../../frontend/src/views/AnalyticsView.vue)。若技术类别数超过 `limit`，返回的 `percentage` 是前 N 项内部占比；当前图表主要使用 `count`。
- **建议与验收**：先写清指标定义。若论文只展示数量，避免把 API 百分比解释为全平台份额；若需要全量占比，确认字段语义后修正计算，构造类别数大于 `limit` 的已知答案数据，并验证分母。

### L6：真实模型测试入口的成本边界

- **代码位置**：[`/ai/test`](../../backend/app/api/v1/ai.py)、[测试服务](../../backend/app/services/ai.py)。入口要求登录，但直接调用 Provider，未形成业务 `AIRequest` 记录和统一额度控制。
- **建议与验收**：本地受控演示可以保留该调试能力。真实 Key 对普通用户开放前，先明确其权限范围并限制或关闭该入口；如保留面向用户的调用，需要纳入 P22 的费用、额度和审计设计。不得把限制测试入口等同于完成 P22。

### L7：跨模块承接是人工流程

- **代码位置**：[社区项目详情](../../frontend/src/views/CommunityProjectDetailView.vue)提供浏览、收藏、评论等操作；[个人项目创建](../../frontend/src/views/ProjectsView.vue)、[学习计划](../../frontend/src/views/LearningOverviewView.vue)和[AI 工作台](../../frontend/src/views/ProjectAIWorkspaceView.vue)各有独立入口。目前没有“把社区作品一键加入本人项目/计划”或“把 AI 建议自动变成学习任务”的已实现操作。
- **判定**：这不是必然的代码缺陷。人工选择、建立本人项目、手动拆任务可以构成可演示的学习流程；项目说明也明确不支持 AI 自动创建每日任务。
- **建议与验收**：在毕业设计主线和论文图中写明人工操作点，演示一次完整手动承接。只有当题目、任务书或论文主张要求自动推荐/自动转化时，才另行定义需求、权限和验收，不为“看起来更完整”而添加功能。

## 四、验证边界与执行顺序

- 本轮运行的 98 项相关后端单元/API 测试通过，覆盖认证、校园身份、教学、提交、个人学习、工作台、ProjectContext、Workflow、社区、统计和报告的选定路径。它们没有覆盖 L1/L2 的新状态组合，也不等于已运行完整后端测试或浏览器及真实 MySQL 总验收。
- L1 的服务层最小样例确认终态计划可接受新任务；L2 的服务层最小样例确认变更计划项目时未查询已有任务。两项均未在本轮对真实业务库写入数据。
- [README 当前状态](../../README.md#当前开发进度)所列 P22/P23 仍为设计检查点，P24 真实班级试点未开始。技术闭环、可复现答辩和真实教学效果应分别下结论。

推荐按 **L1/L2 → L3 → L4 → L5** 收口毕业原型；**L6** 在真实模型 Key 开放前完成；**L7** 先确定论文叙述范围。每项完成后保留“复现样例、决策、改动、回归结果”四类证据。需要改公共 API、持久化格式、数据库、依赖或安全策略时，先说明事实、影响、选项和推荐方案，再确认实施。本清单仅整理问题，尚未授权这些代码改动。
