# ScholarHub 毕业设计整改方案

- 制定日期：2026-09-27
- 文档性质：基于当前仓库的整改计划；不是阶段验收报告，也不表示已取得教师或学校批准
- 适用范围：以“AI 辅助校园学习与代码实践平台的设计与实现”为毕业设计题目，交付可复现的本地原型、论文和答辩材料
- 检查基线：`main` / `3d459ad`，制定本方案时工作区无未提交修改
- 2026-09-27 补充：依据当前源码的只读检查，加入代码设计整改点；这些发现尚未通过本轮新测试验证

## 1. 总体判断与整改目标

ScholarHub 已具备个人项目、学习记录、AI 工作流、教学班任务、成果提交与反馈、校园社区治理等工程能力。现有[项目说明](../AI辅助校园学习与代码实践平台_项目说明文档.md)和[2026-09-25 现状报告](../阶段报告/20260925-项目全量现状与GitHub交付报告.md)将 P00–P21 记为技术交付，P22/P23 记为设计检查点，P24 记为未开始。203 项后端测试和前端类型检查、构建通过是上述报告记录的历史结果；本方案没有重新运行这些检查。

本次整改目标是让毕业设计形成可审查的完整证据链：**问题与需求 → 设计取舍 → 关键实现 → 测试与实验 → 结论和局限 → 可复现答辩**。功能数量、数据库表数和测试数量可以描述工程规模，不能替代研究问题、数据分析结论或真实教学效果。

### 1.1 答辩口径

推荐保留现有题目，不将系统描述为“已投入校园使用”或“已证明提高学习效果”。论文主要讲述一条连续流程：

> 学生选择项目 → 制定学习任务 → 使用 AI 获取有边界的建议 → 记录实践过程 → 查看过程数据与成果反馈。

校园账号管理、社区治理和教学班权限属于支撑模块。答辩主讲其必要的设计边界，详细接口与页面放在附录或追问材料中。AI 的可追溯工作流、学习过程指标和个人/教学数据隔离可作为本项目的设计特点；是否属于学校要求的“创新点”，需由指导教师按任务书确认。

### 1.2 不扩大为校园上线项目

若学校只要求“系统设计与实现及原型验证”，P22 全平台额度与计费、P23 生产部署、P24 真实班级试点不作为本轮毕业交付的前置任务。若论文或学校任务书要求真实部署、真实学生使用或教学效果验证，则必须另行完成相应准入和取证，不能用本地演示替代。[README 当前限制](../../README.md#当前限制与上线门槛)已说明生产与试点缺口。

## 3. 整改工作包

以下工期是净工作时间估计，按学校要求和现有论文材料调整。每完成一个工作包，保存可审查的交付物和验收结果，再进入依赖它的下一项。

### R0：锁定毕业设计范围与主张（约 0.5–1 天，最高优先级）

1. 核对学校任务书：题目、专业要求、论文格式、实验或用户验证要求、最低演示条件、提交日期。
2. 写一页“研究问题与范围”：目标用户、主要场景、三个要解决的问题、明确排除的上线与真实效果主张。
3. 选择论文重点：推荐“项目实践流程中的可追溯 AI 辅助与学习过程数据分析”；不把所有 24 个阶段均作为同等研究重点。

**交付物：**题目与范围确认页、主张清单、任务书要求对照表。

**验收：**论文摘要、系统介绍和演示开场使用同一题目与边界；所有“提升效率、改善成绩、校园应用”等结论均有对应证据或从已完成成果中删除。

### R1：建立论文证据骨架（约 2–3 天，高优先级）

1. 整理需求依据：学生项目实践、教师反馈、学习过程记录各自的使用场景；区分已访谈的真实需求、文献依据和开发者设定的需求。
2. 建立“需求—实现—验证”矩阵，每项核心需求指向实际页面/API/Service/数据表及对应测试或人工验收。
3. 从现有架构图与 ER 图提炼论文图：总体架构、一个主流程时序图、关键实体关系、个人与教学数据权限矩阵。
4. 记录关键取舍：单体架构、MySQL 聚合、版本化 Context、Workflow 运行记录、教师反馈版本冻结和权限隔离。每项写清目标、方案及局限。
5. 列出学校规定的相关研究、参考文献和引用格式；引用必须能核对来源，阶段报告不能充当学术文献。

**交付物：**论文目录与章节提纲、需求矩阵、图表清单、参考文献台账。

**验收：**论文每个核心设计段落都能回到需求与代码；每个“已实现”表述都有当前实现位置；计划中的 P22–P24 不混入已实现章节。

### R2：建立可复现的答辩演示（约 2–4 天，高优先级）

1. 在隔离数据库准备虚构样本：管理员、教师、学生、班级、一个教学任务、V1 提交、退回意见、V2 提交和通过反馈。
2. 保留最小的初始化步骤或脚本、数据说明和清理步骤；不提交真实账号、口令、API Key、本地业务库或个人信息。
3. 从新建库按 [README 启动步骤](../../README.md#本地启动)部署本地原型，按[原型逐页演示指南](../答辩材料/ScholarHub原型逐页演示指南.md)缩成一条 10–12 分钟主线。
4. 对现场模型不可用准备预先记录、明确标注来源的演示结果；不把 Fake Provider 输出当作真实模型评测。
5. 对 C2 必须给出当前版本可通过的主线验收：最小适配旧全链路脚本的校园身份与发布审核前置条件，或交付等效的隔离验收步骤。先保留旧失败现场，不能删除断言或降低权限规则换取通过。

**交付物：**虚构数据说明、从零演示步骤、主线操作记录与截图、故障备用演示方案。

**验收：**在不同于当前业务库的环境中，学生与教师按权限完成“任务—提交—退回—重交—反馈”；刷新后记录仍可查询；演示不依赖 74 个本地项目，C2 有当前版本的通过证据或明确阻断结论。

### R3：补齐数据与 AI 评价（约 4–6 天，高优先级）

#### A. 学习过程数据

1. 定义指标字典：统计对象、时间范围、时区、去重方式、缺失值和分母。例如“当日访问人数”与“浏览次数”分开解释。
2. 用已知答案的虚构数据验证 7 日/30 日趋势、跨日时区、项目状态与任务完成口径，保留输入样例和期望值。对 C4 另加“技术类别多于返回上限”的样例，区分全量占比与前 N 项占比。
3. 在隔离环境按小、中、较大三档虚构数据量重复查询，记录环境、数据量、查询耗时和异常；具体规模依据电脑能力选定。该实验只评估当前实现的容量表现，不把万级样本称为“大数据”。

**验收：**论文中的图表指标可以手工复算；C4 的分母与文字口径一致，未确认前不引用其百分比；性能结论只覆盖测试环境和测试数据规模。

#### B. AI 辅助质量

1. 只选 2–3 个与主线最相关的场景，例如需求分析、代码讲解和答案评审，准备 12–20 个固定、脱敏样例。
2. 评测前固定模型/Provider、提示词版本、输入和评分规则；至少记录结构通过率、与输入事实一致性、建议可执行性、失败类型、延迟与 token 用量。
3. 若论文声称“工作流优于直接提问”，应在相同样例和模型条件下设置直接提问基线。没有该比较，就只评价本系统输出，不写优越性结论。
4. 如有真实教师评阅，记录评阅标准、样本数和意见；没有教师时，可做工程质量评价，但不能推断教学有效性。
5. 若无法承担真实模型费用，只保留 Fake Provider 的流程可靠性测试，论文明确不评价真实模型内容质量。
6. 对 C1 加入“结构有效但事实数字错误”的 Fake Provider 样例，比较报告结果与同次聚合输入；在获得必要的接口/持久化变更确认后，采用最小修复并补回归测试。对 C3 明确 `/ai/test` 的开放范围与费用记录；真实 Key 面向非受控账号前先处理最小入口限制，不将完整 P22 偷渡进毕业整改。

**验收：**评测结果能从样例、评分表和原始输出重新计算；C1 的数字一致性有可复现结论，C3 的开放边界和费用风险有明确处理决定；失败案例与局限和成功案例一起呈现。

### R4：集中修正文档与验证结论（约 2–3 天，中优先级）

1. 统一根 README、项目说明、`PRODUCT.md`、知识网络进度页和答辩指南的状态；历史文档保留日期，不无差别改写阶段记录。
2. 在最终修改完成后运行现有后端测试、前端类型检查和构建、适用的浏览器回归及隔离 MySQL 主线验收；记录命令、时间、通过/失败和环境。
3. 对发现的问题按“阻断答辩、影响主线、仅扩展模块”排序；只修复影响当前毕业交付的缺陷。涉及公共 API、数据库、依赖或安全策略时，先列事实、影响、选项和推荐方案，再确认实施。
4. 逐项收口 C1–C4：列出复现样例、决定、代码/文档变化、回归结果或未完成原因。C5 按 R0 的部署范围记录为已知局限或 P23 事项，不冒充毕业原型必须重构的架构缺陷。

**交付物：**状态一致的文档、最终测试记录、未解决问题清单。

**验收：**同一功能在论文、README、演示指南中只有一种当前状态；C1–C4 没有无解释的悬空结论；旧报告中的 203 项测试不被冒充为本次新验证结果。

### R5：论文成稿与答辩排练（约 3–5 天，最高优先级）

建议论文章节：绪论与相关工作、需求分析、系统设计、关键实现、测试与实验、总结与局限。正文重点展示三个关键技术点及其评价，不逐页罗列 30 个页面。图表写来源与口径；截图标注演示数据或真实运行记录。

答辩准备：一份 10–12 分钟 PPT、一条主线现场演示、可离线查看的证据截图、常见追问答案。重点练习解释数据统计口径、AI 幻觉与质量边界、权限设计、为何尚未进行真实班级试点。

**验收：**完成两次计时排练；出现网络、模型或开发数据库故障时仍能准确说明已实现功能和已有证据；论文与演示不展示秘密或真实学生信息。

## 4. 推荐执行顺序与完成门槛

```text
R0 范围确定
  → R1 论文证据骨架
  → R2 可复现演示 ─┐
  → R3 数据与 AI 评价 ├→ R4 状态和验证结论 → R5 论文定稿与答辩
                       ┘
```

在 R0 完成后，R1 可与 R2/R3 部分并行，但实验方法应先写清再收集结果。纳入 C1–C4 的复现与必要最小修复后，整体估计约 **14–22 个净工作日**；具体用时受学校材料、确认门槛和测试结果影响，不代表学校截止日期或已完成进度。

最终交付至少包括：

- 与学校模板一致的论文及参考文献；
- 需求—实现—验证矩阵、关键架构图和数据指标字典；
- 可复现的虚构演示数据与操作说明；
- 数据统计和所选 AI 场景的实验记录，或明确未评价的边界；
- 最终版本的测试记录、PPT、演示截图与已知局限。

完成判据是：指导教师能核对选题与任务书，另一位开发者能复现核心演示，论文主要结论均有可追溯证据。正式答辩资格和评分以学校要求为准。
