## 2. 最小部署拓扑

推荐采用校方管理的一台 Linux 虚拟机，并复用校方已有 Nginx、证书和 systemd；如果实际服务器不是 Linux，应在确认后把服务管理模板改为对应平台，不能先写一个无法使用的部署脚本。

```text
受控校内网络或 VPN
        │ HTTPS 443
        ▼
Nginx（静态 Vue + /api/v1 反向代理）
        │ 127.0.0.1:8000，可信代理仅本机
        ▼
Uvicorn 单进程单 worker（无 --reload）
        │ 127.0.0.1:3306
        ▼
MySQL 8（独立最小权限运行账号）
```

- Nginx 提供 Vue SPA 回退和同源 `/api/v1`；Uvicorn 与 MySQL 不直接暴露到校园网络。
- Uvicorn 使用单 worker，直到进程内滑块、敏感操作限流和 AI 运行状态被替换为共享状态并重新验收。单实例适合有界试点，不代表高可用。
- 不引入 Docker、Redis、Celery、Kafka、Kubernetes、微服务或新监控平台。
- 默认访问范围为校内/VPN；公网方案、DNS 和防火墙只有在域名与校方审批明确后单独执行。

## 3. 待确认后的最小代码与配置变更

### 3.1 生产配置与反向代理

推荐新增无秘密的生产配置模板和启动前校验：

- 后端增加明确的 `APP_ENV=development|production`、`API_DOCS_ENABLED` 和 `TRUSTED_HOSTS`；生产模式缺少数据库、JWT、HTTPS CORS、可信 Host 或 P22 配额配置时启动失败。
- 保留 `/api/v1/health` 作为兼容存活检查，新增 `GET /api/v1/health/ready`。就绪检查只执行有超时的 `SELECT 1` 并返回脱敏的 200/503；服务启动前另运行现有数据库结构检查，避免每次探针都做全库反射。
- 前端生产 API 地址使用同源 `/api/v1`；开发环境继续显式配置 `http://127.0.0.1:8000/api/v1`，防止把本机地址写进部署产物。
- Nginx 只转发本机 Uvicorn，传递 Host、协议和请求 ID；Uvicorn 仅信任 `127.0.0.1` 的代理头。AI/Workflow 总超时为 90 秒，反向代理读超时应略高于该上限，但不改成无界等待。
- Swagger/OpenAPI 在生产默认关闭；确需开放时只允许维护网络访问。HTTPS 验证通过后再启用 HSTS；同时配置 `nosniff`、Referrer Policy、frame 限制和与当前 Vue/ECharts 兼容的 CSP。
- Nginx 限制请求体并隐藏版本信息。项目没有文件上传，推荐初始上限 1 MiB；若实际需求证明不足再调整。

这些变更会修改构建与安全策略，并新增一个公共就绪 API，必须在用户确认后实施。它们不需要新增第三方依赖。

### 3.2 数据库权限

推荐使用三个边界清晰的主体：

1. 运行账号：仅对 `scholarhub.*` 具有业务所需的 `SELECT/INSERT/UPDATE/DELETE`；不具备全局权限、建库、建用户、文件、关机或授权权限。
2. 迁移账号：只在维护窗口使用，由负责人保管；应用进程不持有该凭据。
3. 备份账号：只具备逻辑备份所需的只读权限；凭据通过受权限保护的 MySQL option file 提供，不写命令行、脚本、日志或 Git。

先在隔离库验证授权，再切换试点配置。当前 `root@localhost` 只可用于本地开发维护，不能直接复制到目标服务器。

## 4. 运行可靠性与故障处理

### 4.1 可观测性和告警

- 继续使用现有 JSON 标准输出和 `X-Request-ID`；由校方现有服务管理/日志能力收集并轮转，不在应用内新增日志平台。
- 最小监控项：存活、数据库就绪、HTTP 请求数/5xx/延迟、进程 CPU/内存、磁盘剩余、MySQL 连接，以及 P22 落地后的额度余量、未知用量和拒绝次数。
- 告警必须绑定真实接收人和值守时段。推荐触发：连续 3 次就绪失败、5 分钟 5xx 超过已确认阈值、磁盘低于 20%、AI 平台额度低于 10%或出现未知用量。阈值需在压测后校准。
- 故障顺序：暂停邀请和新 AI 调用 → 保留只读查询 → 记录请求/运行 ID → 判断数据库、进程或供应商故障 → 恢复后先查询既有运行记录再允许重试。

### 4.2 AI 长任务与重启

现有 AI 与 Workflow 是同步 HTTP 调用，没有持久化后台任务队列。进程退出时，供应商可能已经收到请求或产生费用：

- Workflow 遗留 `running` 可在下一次运行超过恢复时限后标记失败；该机制不是自动恢复执行。
- 独立 Agent 和 `/ai/test` 没有完整的跨进程恢复链路；浏览器断线也不能证明服务端或供应商调用已取消。
- P22 应先把重试、未知用量、平台开关和并发限制统一落库。P23 重启演练只使用 Fake Provider，验证旧运行可查询、不会伪造成功、用户需要明确重试。
- 若确认的课堂并发或恢复目标证明同步调用不够，再单独提交最小持久化任务方案；本阶段不提前引入任务队列。

## 5. 备份、恢复与容量演练

推荐默认目标供确认：每日一次逻辑全备、滚动保留 30 天，RPO 24 小时、RTO 4 小时。备份放在校方控制且与应用目录分离的位置，限制到维护者/备份服务账号；备份含私人和教学数据，不能进入 Git、Web 根目录或普通共享盘。

演练步骤：

1. 在目标环境维护窗口暂停写入或确认一致性快照条件。
2. 使用 `mysqldump --single-transaction` 和受保护的 option file 导出；日志只记录时间、结果和文件大小，不记录凭据或正文。
3. 在隔离数据库创建恢复目标，禁止覆盖当前业务库。
4. 导入后运行数据库连接、34 张现有表及后续 P22/P23 表结构检查。
5. 用虚构账号核对身份授权、班级/任务/提交/反馈、Workflow 运行和治理记录的关联与计数。
6. 记录实际备份时间、恢复时间、失败点和清理结果；隔离恢复库在证据保留后受控删除。

未经确认不创建备份计划、不导出当前库、不新建恢复库。恢复演练授权不等于允许覆盖业务库。

推荐首轮有界压测参数供确认：40 个虚构用户、普通 API 10 并发、AI 平台 2 并发/单用户 1 并发；普通读取 p95 小于 1 秒、写入 p95 小于 2 秒、5xx 小于 1%，且不得出现越权或重复副作用。AI 延迟单独按 Provider 和既有 30/90 秒上限报告，不把供应商等待混入普通 API 指标。真实人数、服务器规格和费用上限未确认前不执行 AI 压测。

### 6.2 用户可见说明与导出删除

确认后推荐新增一页与实际功能一致的校园试点隐私说明，并在每个 AI 运行入口显示：供应商、将发送的数据类别、不会发送的私人类别、可能产生费用、模型结果仅供参考及主动运行按钮。页面不虚构备案、校方批准或法定期限。

留存建议沿用 P16、等待校方确认：

- AI Context 快照和结果 30 天；提交/反馈在结课后 90 天处理；通知结课后 30 天；请求日志 30 天；账号/治理审计 180 天；备份滚动 30 天。
- 旧个人数据不因试点退出自动删除；校园资格撤销与私人账号注销分开。
- 恢复备份后重放已经批准的删除清单，避免被删数据重新出现。

导出/删除有两种方案：

- 方案 A：只提供运维人工流程。改动小，但申请状态、授权和处理证据分散，容易遗漏。
- **方案 B（推荐）**：新增一张最小 `privacy_requests` 表，记录本人提出的 `export/correction/deletion` 请求、白名单范围、状态、处理人、原因、UTC 时间和 revision；本人只能查看自己的请求，管理员只看请求元数据。本人导出由后端按 owner 过滤生成有界 JSON，不包含密码摘要、Token、他人信息或内部审计备注；删除先生成范围预览，按已批准留存规则处理，提交/反馈和治理证据不能被无条件级联删除。实际执行需要对应请求与维护者的单次授权。

方案 B 会新增数据库表和公共 API，只有在留存期限、请求处理负责人和响应时限确认后实施。它不创建管理员全体导出接口，也不把备份文件放入 Web 下载目录。
