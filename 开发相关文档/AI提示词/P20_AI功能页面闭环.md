# P20 AI 功能页面闭环：可直接投喂给 AI 的提示词

基于现有 P09-P13 的 Workflow、ProjectContext、Provider、Agent 与 Engine，以及已完成的校园身份和教学模块，补齐 `ScholarHub` 的 AI 用户操作页面。本阶段让学生不用 Swagger 也能使用已实现能力，不增加新 Agent 类型或新的执行引擎。

## 先检查现状

读取工作区规则、前后端目录职责、AI 提示词 README、P16 确认方案和最新交付报告。逐项核对 Context 创建/读取/更新、Agent 调用与结果查询、Workflow graph/run/runs 的真实路径、Schema、版本、状态和超时。

检查前端 WorkflowCanvas、工具栏、配置与结果面板、Store 和 Axios 封装。先列出已有 API 与页面缺口，不将“图检查”面板当作节点运行结果，不假定当前运行接口已经是异步任务接口。

## 本阶段目标

- 提供所属 Project 的 Context 编辑与查看：核心字段、版本、更新时间、来源、校验错误及冲突处理；保存使用现有版本协议。
- 提供需求分析和开发 Prompt 操作，输入与结果按明确类型展示；结果能够刷新查询、复制和区分成功/失败，不直接渲染模型返回的任意 HTML。
- 在现有 Workflow 页面加入运行入口、运行记录、节点状态和结果详情，优先支持已注册的需求分析 → 技术栈分析 → 架构设计三节点。
- 未注册的节点类型不能让用户误以为能够执行；使用真实能力禁用或解释，不为展示完整性伪造运行结果。
- Context 或技术栈变化后，明确显示 stale 和受影响节点，用户确认后再重新生成；不能因字段变化自动产生付费调用。

## 实现边界

1. 沿用 Vue 3、TypeScript、Vue Flow、Element Plus、Pinia、Axios 和现有 FastAPI + SQLAlchemy + MySQL 分层，不引入第二套 UI、Agent 框架或 WebSocket。
2. 页面、画布、工具栏、输入配置、结果展示、请求和 Store 保持职责清晰。API 集中在 `src/api`，没有 `any`、双重断言或组件直连 Provider。
3. 根据真实 HTTP 协议处理运行中、失败、超时和重试。优先复用有界运行与结果查询；若需要改为返回任务 ID 的后台执行，先说明 API 兼容性和恢复方案并等待确认，不直接重写引擎。
4. 查询采用有上限的轮询或主动刷新，离开页面取消查询或忽略旧响应；浏览器取消请求不代表服务端模型任务已取消，不显示不存在的“取消成功”。
5. 运行失败、版本冲突、超时或网络中断后先查已有运行记录，再由用户明确选择重试，避免无条件重复调用模型。
6. 用户只能读取和运行其有权访问的 Project/Workflow；教师身份不自动扩大私人 Context 和 AI 结果的权限。模型输出不成为权限、命令或自动修改依据。

## 交互要求

遵循 `$frontend-backend-code-standards` 和既有界面设计说明。保留冷白、海沫绿、钴蓝基调；将过渡、液态分段选中和状态反馈用于清晰表达操作，不重做全站。

具备加载、空、成功、失败、不可用、冲突和重试状态；防重复运行，长文本可阅读，键盘、窄屏和减少动态效果可用。任何新增依赖、公共 API、持久化格式或数据库变更先说明事实、影响和方案并等待确认。

## 验收标准

- 通过页面完成 Context 创建与修改 → 需求分析 → 生成 Prompt → 查询结果，全程不依赖 Swagger。
- 页面编辑、保存并运行三节点 Workflow，刷新后恢复运行记录、节点结果和 Context；修改技术栈后 stale 明确可见，重新生成后状态按后端结果更新。
- fake Provider 下覆盖成功、输出格式错误、Provider 失败、超时、重复提交、版本冲突、越权和会话失效；缺少 API Key 时显示真实配置错误。
- 浏览器验证桌面、窄屏、长结果、刷新恢复和路由切换，不把模拟响应冒充真实模型成功。真实 Provider 验收须在用户明确授权的费用上限内执行。
- 原有图保存、拖拽和连线测试保持通过；重要能力未实现时如实标记边界。
