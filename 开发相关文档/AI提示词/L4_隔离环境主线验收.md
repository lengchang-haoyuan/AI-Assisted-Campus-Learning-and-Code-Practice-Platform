## 先检查环境与已有工具

读取 [旧全链路脚本](../../backend/scripts/verify_integration.py)、[P21 隔离验收](../../backend/scripts/verify_p21_governance.py)、[统计与报告验收](../../backend/scripts/verify_statistics_reports.py)、[工作流验收](../../backend/scripts/verify_workflow_engine.py)、[README 启动说明](../../README.md)、现有身份/教学/提交 API 与测试。

1. 保留旧脚本普通账号访问社区的失败证据；该失败不能自动解释为产品故障。
2. 比较最小适配旧脚本与复用现有工具组合的方案，推荐满足本步验收且重复最少的一种，不创建第二套无关测试框架。
3. 检查目标 MySQL 是否为明确的专用隔离环境；只记录环境类别和非敏感标识。目标不明时不执行任何建库、写入或清理。
4. 先准备可审查的虚构样本、环境命令和资源清单。新依赖、校验策略或有影响的数据库操作按共同约束确认。业务库不得被自动清空、迁移或用作临时样本库。
5. 模型边界默认用现有测试替换注入 Fake Provider，不假定项目已有某个不存在的环境开关。

## 验收主线

按当前合法权限准备管理员、教师、学生及另一组对照主体，使用现有受控初始化和邀请流程：

- 注册/登录 → 校园身份取得 → 合法班级与成员。
- 本人创建项目 → 学习计划 → 任务完成 → 学习记录 → 可重新查询的个人数据。
- Context/Workflow 保存与运行 → 结果查询；至少一次受控失败和恢复/续跑。
- 学习报告正确事实与失败状态；补齐 L1/L2/L3 尚未完成的真实持久化验证。
- 作者发布申请 → 管理员审核 → 有效校园用户浏览公开快照与互动。
- 教师任务草稿/发布 → 学生提交 V1 → 教师退回并通知 → 学生提交 V2 → 教师通过 → 双方查历史。
- 验证跨用户/跨班级访问被拒绝；通过事件不伪造学习时长，也不自动等同于个人任务或 Project 完成。
- 若 L5 改了统计语义，加入超过返回上限的已知答案数据；按 L7 的人工步骤演示跨模块承接。

## 实施与证据

- 必要改动限定在验收脚本、虚构 fixtures 和相关使用说明；若发现业务缺陷，先定位失败和最小修复，不静默扩大到其他 L 阶段。
- 复用真实 API/Service 与实际数据库查询；Mock 整条业务链不能作为 MySQL 验收结果。
- 浏览器主线独立记录。API 成功不等于 UI 成功；需刷新并重新查询关键项目、状态、版本、反馈和报告，保留脱敏证据。
- 脚本创建与清理的资源明确可追踪，正常和异常路径均能处理自己创建的测试数据；不删除既有业务资源，不吞异常。
- 环境无法运行时保留可执行命令、样本及具体阻断点，结论为待环境验证。

## 完成条件

交付当前版本可重复执行的主线步骤/工具、虚构样本说明、成功/失败证据和逐项验收矩阵。实际运行项目已定义的后端测试、前端类型检查与构建、适用浏览器回归和隔离 MySQL 验收；仅对具体剩余风险补充检查。报告不得将旧 98/203 项或某个专项通过替代本轮总主线结论。
