# ScholarHub 代码闭环整改提示词使用说明

- 制定日期：2026-09-28
- 来源：[项目逻辑与代码闭环缺口清单](../开发规划/20260927-项目逻辑与代码闭环缺口清单.md)
- 配套：[毕业设计整改总方案](../开发规划/20260927-毕业设计整改方案.md)
- 本组用于处理 L1–L7；每个文件可以整体复制给能读取当前 ScholarHub 仓库的 AI。生成提示词不代表代码已修复，也不批准模型费用、生产上线或未来高影响变更。

## 如何投喂

1. 打开当前 ScholarHub 工作区，每次只复制一个 L 文件全文。
2. AI 应先核对当前代码和最新验收；2026-09-27 的清单是检查起点，不能代替现在的事实。
3. 一个缺口完成后，检查其报告、差异和验收证据，再投喂下一步。待确认、未验证与已完成应分开记录。
4. 如果沿用同一任务，保留上一步的决策；如果换一个 AI 任务，附上上一步完成报告和仍待处理的问题。
5. L 文件均不自动授权 Git 提交或推送；本组规则优先于旧 P 阶段提示词中的历史提交约定。

## 文件与执行顺序

编号对应缺口编号，不是强制执行次序。推荐代码整改顺序：**L1 → L2 → L3 → L5 → L4**。L7 的范围梳理可以在开始时完成；L6 在真实模型 Key 对非受控账号开放前执行，并将结果纳入 L4。

| 文件 | 执行目标 | 验收重点 |
| --- | --- | --- |
| [L1 终态学习计划与任务约束](L1_终态学习计划与任务约束.md) | 补齐计划终态与任务变更规则 | 创建、改挂与其他必要入口不能破坏状态/进度；合法幂等不受损 |
| [L2 计划与既有任务一致性](L2_计划与既有任务一致性.md) | 修改计划时校验已有任务 | 项目及日期冲突被拒绝，合法编辑保持可用 |

## 与 R 整改路线的关系

- L1/L2 补充总方案原先没有单列的学习计划不变量；其结果交给 R4 汇总。
- L3 对应原 C1/R3B；L4 对应原 C2/R2；L5 对应原 C4/R3A；L6 对应原 C3/R3B。
- L7 为 R0/R1 的范围和主张提供事实依据。
- L 系列处理代码和主线验证，不代替论文评价、数据实验、答辩材料和真实课堂试点。R 阶段再次执行时读取 L 阶段结果，不重复修改已经验收的代码。

## 最终收口

每项必须留下以下一种结论，并指向证据：已修复并验证、已按确认口径限定、待用户决策、待环境验证、条件未触发。L4 在相关修复完成后执行；若之后又改变核心流程，补跑受影响的验收。仅有文档、Mock 调用或测试数量不能证明真实持久化与浏览器主线已通过。
