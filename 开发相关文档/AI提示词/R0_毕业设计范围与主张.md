# R0 毕业设计范围与主张：可直接投喂给 AI 的提示词

现在执行 ScholarHub [毕业设计整改方案](../开发规划/20260927-毕业设计整改方案.md)中的 **R0**，本次只确定毕业设计范围与主张，不开发功能。请先读取当前工作区规则、该整改方案、根 README、项目说明、最新阶段报告和已有答辩材料；以当前 Git 与文件为准，不将历史规划写成当前实现。

## 本步目标

1. 查找用户已经提供的学院任务书、论文模板、评分标准和截止时间。仅在可达材料中查找，不臆造学校规定，也不把仓库内没有文件等同于用户没有文件。
2. 基于已核实的项目现状，起草一页“题目与范围”：目标用户、主场景、三个核心问题、预期交付、明确局限。推荐保留“AI 辅助校园学习与代码实践平台的设计与实现”的题目口径；是否调整题目以学院材料为准。
3. 建立主张清单，逐条标为“可由当前代码证明”“需 R2/R3 验证”“需真实教师/学校确认”“不纳入本次毕业交付”。重点检查“已校园应用”“提升成绩/效率”“AI 内容正确”“具备大数据处理能力”等说法。
4. 建立任务书要求对照表：要求、证据来源、当前状态、缺口、负责确认者。任务书未提供时，用“待提供”标记并继续完成项目事实部分。

## 交付与边界

- 将范围页和对照表放在 `开发相关文档/开发规划/`，与现有整改方案互相链接；如同名文件已存在，先检查再小幅更新。
- 主线固定为“选择项目 → 制定学习任务 → 使用有边界的 AI 建议 → 记录实践 → 查看过程数据与成果反馈”。校园治理与账号管理是支撑模块。
- 不改运行时代码、数据库、依赖、公共 API，不开始 P22–P24，不联系教师或学校，不替用户确认题目或批准真实试点。
- 若学院要求与推荐范围冲突，列出事实、影响和推荐调整；需要用户或指导教师决定的内容保持待确认。

## 完成判据

- 范围页能直接用于论文摘要和答辩开场，三者不会出现不同题目或不同完成状态。
- 每条关键主张都有当前证据、后续验证任务或明确局限；没有把技术验收写成教学效果。
- 按现有目录约定追加中文时间索引操作记录和本步报告。最终用中文汇报新增/修改文件、材料来源、已核实结论、待确认问题和进入 R1 的条件。不要提交或推送 Git；只给出必要的 commit 建议。
