# P19 成果提交与教师反馈：可直接投喂给 AI 的提示词

基于 P18 班级和教学任务，为 `ScholarHub` 实现成果提交、版本历史、教师反馈和必要的站内通知。本阶段完成最小教学闭环，不做文件上传、代码执行、自动评分或 Git 平台集成。

## 先检查现状

读取工作区规则、前后端目录职责、AI 提示词 README、已确认 P16 方案和 P17/P18 实际产物。检查任务发布与截止规则、成员权限、Project 私有性、学习记录和现有通知能力，不因规划提及通知就假定已有实现。

沿用 Vue 3 + TypeScript + Element Plus、FastAPI + SQLAlchemy + MySQL。按 Router → Service → Repository 分层；新增依赖、公共 API、持久化格式或数据库变更先说明影响并等待确认，不重建已有模块。

## 本阶段目标

- 学生提交文字说明、合法仓库链接、代码版本标识，并可关联自己拥有的 Project；明确这些是提交证据，不表示系统已经拉取或验证仓库代码。
- 提交形成可查询版本，重复点击或网络重试不能生成无界重复版本；教师查看学生已提交内容，不自动读取关联 Project 的全部私人字段。
- 教师对指定提交版本反馈、退回修改或确认通过；保留历史意见及对应版本，学生修改后重新提交，旧记录不能被静默覆盖。
- 学生和教师分别有待处理列表与详情页，显示任务截止、提交时间和处理状态；需要时复用已有项目页面而非另建工作台。
- 提供站内通知列表、未读状态和已读操作，用于任务发布、收到反馈等必要事件；采用普通 API 查询或有界轮询，不新增 WebSocket、邮件、短信或推送平台。

## 业务与安全要求

1. 按 P16 明确首次提交、退回、重新提交、通过、逾期和任务关闭后的允许动作；后端执行规则，不能只禁用前端按钮。
2. 校验提交者是当前有效班级成员、任务属于该班级、关联项目属于本人；教师操作需校验班级授权和提交版本，过期版本反馈不得误作用到新版本。
3. 提交版本与状态变更使用事务或版本校验；通知落库与关键操作保持一致，刷新和重试不重复产生通知。通知只能由接收人读取或标记。
4. 仓库 URL 只允许确认过的安全协议，不接受脚本 URL、带认证凭据的链接或自动访问内部地址；本阶段不由服务器抓取链接，避免引入任意网络请求能力。
5. 学生私人笔记、Context、AI 输入不随关联 Project 自动暴露。收到退回或通过反馈，不自动生成学习时长、AI 报告，也不把个人 Project 强制改为完成。
6. 明确退出班级、账号停用、任务归档后的提交历史访问与保留规则；不能通过删除项目级联抹掉应保留的教学提交记录。

## 前端与测试

遵循 `$frontend-backend-code-standards`；API 集中在 `src/api`，不使用 `any` 或双重断言。版本、退回和通过都有文字反馈，危险操作确认，加载、空、失败、重试及重复提交状态完整；动效沿用现有组件并支持键盘、窄屏和减少动态效果。

API/Service 与数据库测试覆盖成功链路、跨班级访问、关联他人项目、非法链接、截止边界、重复提交、并发反馈、旧版本冲突和通知越权。使用隔离样本，不访问真实外部仓库或采集学生个人数据。

## 验收标准

教师发布任务 → 学生提交 V1 → 教师退回并反馈 → 学生收到通知 → 学生提交 V2 → 教师确认通过 → 双方刷新后仍能查询各版本与反馈。另一学生及无关教师不能读取该提交，私人项目非提交内容不可见。
