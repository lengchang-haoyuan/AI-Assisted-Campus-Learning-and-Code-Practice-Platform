# P16 试点需求与数据设计：可直接投喂给 AI 的提示词

基于 `ScholarHub` 已有 P00-P15 及后续实际代码，为“一所学校、一门项目实践课程、一个班级”的校园试点确定最小产品方案。本阶段只输出可审查的设计文档，不开发业务、不执行迁移、不创建管理员或真实学生账号。

## 先检查现状

读取工作区 `AGENTS.md`、根 README、`开发相关文档/README.md`、项目说明、前后端目录职责、AI 提示词 README 和最新阶段报告。检查 Git 状态、实际路由、Models、schema.sql、迁移、认证、AI 与前端入口，报告已实现、仅有 API、尚未实现和待确认的内容，不因提示词文件存在就认为阶段已完成。

沿用 Vue 3、TypeScript、Vite、Element Plus、Pinia、Axios、Vue Flow、ECharts，以及 FastAPI、Pydantic、SQLAlchemy、MySQL。保留当前 Provider、Agent 和 Workflow Engine；学生、教师、管理员共用一个前端，后端保持单体分层。

## 本阶段目标

1. 明确试点负责人、目标课程、学生范围、访问方式、AI 费用承担者及技术维护者。未提供的信息列为待确认，不虚构学校、教师或批准记录。
2. 定义最小教学链路：教师发布任务 → 学生提交成果 → 教师反馈或退回 → 学生修改 → 形成学习记录 → 自愿发布校园作品。
3. 定义学生、教师、管理员三个固定角色，以及“主体、资源、动作、授权范围”的权限矩阵；管理员管理账号和公开内容，不默认读取私人学习笔记、Context 或 AI 输入。
4. 区分个人 `Course`、`DailyTask`、`Project` 与教学班级、成员、教学任务、提交版本和反馈。教师名字字符串不等于教师身份，不能把现有个人课程直接改成全班可读。
5. 给出上述核心实体的 ER、字段职责、主外键、唯一约束、索引、状态流转、UTC 时间、归档和删除语义。班级阅读权限优先针对已提交快照或专用响应，不扩大为整个私人 Project 的权限。
6. 输出前端页面及 API 契约草案，优先复用已有页面、路由和组件。明确 P17-P24 的先后依赖、每阶段交付边界和试点退出条件。

## 关键取舍

- 初期采用教师或管理员核验的邀请制；学校统一身份认证留到有实际对接条件时。明确已有用户如何保留账号和数据，以及校园成员资格与已有登录状态的区别。
- 角色与邀请、注册、改密、账号停用、会话撤销的关系在此确定。不得设计通用权限编排平台或内置默认管理员密码。
- 成果提交先接受受校验的文字和仓库链接，不上传或执行代码。教学完成、项目完成、学习时长和 AI 报告之间不能互相伪造状态。
- 明确哪些数据可送外部模型、谁可查看报告、保留多久以及导出和删除边界。具体校方政策未知时保持待确认，不把技术方案当作合规批准。
- 写出增量迁移、历史数据处理、接口兼容及回退或前向修复方案；只设计后续所需边界，不一次创建所有未来表或空模块。

## 执行要求

遵循 `$stop-that-shit` 和 `$frontend-backend-code-standards`。设计文档统一放到 `开发相关文档/开发规划/`，命名包含 P16 和中文主题；不修改运行时代码、锁文件、数据库、线上服务或历史迁移。

对新增依赖、公共 API、持久化格式、数据库结构和部署方案的建议，列出事实、风险、选项和推荐意见，等待用户确认。本提示词与路线图不是这些具体变更的预先授权。

## 验收标准

- 权限矩阵覆盖学生之间、不同班级教师之间以及管理员与私人数据之间的边界。
- ER、页面、API、状态和验收场景使用同一套名称与关系，没有个人课程被隐式公开等兼容性冲突。
- 至少描述加入班级、发布任务、重复提交、退回修改、成员退出、任务归档和私人项目取消共享的结果。
- 明确区分“设计草案已完成”“用户已确认”“教师已确认”“校方已批准试点”；未取得确认的事项不能标记通过。
- 有明确可开始 P17 的确认清单；关键问题未决时只交付草案，不进入业务开发。
