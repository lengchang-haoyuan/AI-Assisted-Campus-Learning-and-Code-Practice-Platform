## 使用方式

1. 先把当前项目根目录设置为 `C:\Users\Administrator\Desktop\毕业设计\ScholarHub`。
2. 每次只向 AI 投喂一个阶段文件，不要把多个阶段合并执行。
3. AI 开始前必须扫描当前代码和文档；阶段完成后先看懂修改，再执行启动、测试和手工验收。
4. 当前阶段通过后再进入下一个阶段。按既有约定只提交本节点修改并推送，核对远端提交；不得强推、覆盖无关工作或用提交记录代替验证。未完成时留下准确检查点。
5. 如果 AI 要新增依赖、修改已经确定的数据库结构、改变公共 API 或采用与文档不同的架构，先让它说明事实、风险、方案和推荐意见，得到确认后再实施。
6. 继续校园试点路线时先投喂 P16。它只做设计和确认，不改业务代码；P17-P23 按已确认方案实施，P24 需要真实试点条件。生成提示词或同意路线不等于批准全部未来变更、模型费用或对外上线。

整改路线每次也只投喂一个 R 或 L 文件，顺序见下表及 L 系列使用说明。上面第 4 条关于 P 阶段提交、推送的历史约定**不自动授权 R/L 阶段提交或推送**；R/L 阶段以各文件的边界为准。

## 后续技术与范围约束

- 沿用现有 Vue 3、TypeScript、Vite、Element Plus、Pinia、Axios、Vue Flow、ECharts 与 FastAPI、Pydantic、SQLAlchemy、MySQL；锁文件决定包管理器，不静默安装或升级。
- 学生、教师、管理员共用一个前端；后端保持单体和 Router → Service → Repository 分层，复用现有 Provider、Agent 与 Engine，先维护一个已配置的 AI 供应商。
- 不默认加入 Redis、Celery、Kafka、Kubernetes、微服务、向量数据库或 LangChain。Nginx/HTTPS 等部署内容到 P23 按服务器条件确认；Docker 不作为试点前提。
- 个人课程、任务、学习记录与教学班级、任务、提交分开授权；管理员和教师不默认读取所有私人数据。数据库只做已批准阶段的增量迁移，不重建或清空既有数据。
- 保持已有设计基调，适量使用液态选中、过渡和状态反馈；高级交互必须兼容键盘、窄屏和减少动态效果，不新增依赖只为装饰。
- 原始学生数据、凭据、完整敏感 Prompt 和真实备份不得进入 Git；fake Provider 默认用于自动化测试，真实调用按明确授权的费用范围执行。
- 长任务方案与部署拓扑保持一致，进程内任务或锁不冒充跨进程持久化与一致性；只有实际证据证明必要才提出后台任务或共享组件方案，并先确认。
- 不做私信、关注、在线 IDE、任意代码执行、自研模型、复杂推荐或全校多租户平台。校方组织和统一身份对接在有真实需求及条件后再单独规划。

## 所有阶段都必须遵守

- 安全性优先，其次是正确性，再考虑可读性和复用。
- 先检查现有实现和文档，再修改；空项目才创建基础结构。
- 只完成当前阶段，不提前实现后续阶段，也不顺手重构无关内容。
- 不硬编码密钥、密码、Token、数据库密码或机器专属路径；提供 `.env.example`，真实值只放本地环境变量。
- 外部输入必须在边界校验；前端校验不能代替后端校验；受保护资源必须在服务端校验所有权。
- 前端只通过 Axios 调用 FastAPI，不直接访问 MySQL；后端遵守 Router → Service → Repository → SQLAlchemy → MySQL 分层。
- AI 通过 AIProvider 抽象接入；模型输出必须当作不可信输入，使用 Pydantic 或等价 schema 校验，不允许无界循环或任意系统命令执行。
- API 使用 `/api/v1` 前缀、明确的请求和响应 Schema、稳定的错误语义；不要直接返回 ORM Model。
- 每完成一组功能立即验证。不能执行的检查要说明命令、原因和剩余风险，不能声称已通过。
- 汇报中不得输出密钥、Token、密码、完整敏感提示词、个人隐私或内部堆栈。
- 遵循当前工作区 `AGENTS.md`、`$stop-that-shit` 与 `$frontend-backend-code-standards`；前端类型明确、API 集中，后端独立验证授权与输入，保护已有用户修改。
- 累计日志放 `开发相关文档/开发日志/开发操作日志.md`，单次报告放 `开发相关文档/阶段报告/`，设计放 `开发相关文档/开发规划/`，可公开的脱敏截图放 `开发相关文档/测试证据/`；不恢复已废弃的旧文档目录。

## 每阶段固定汇报格式

完成后必须汇报：

1. 修改和新增文件清单。
2. 本阶段关键设计和调用链。
3. 启动命令及必要环境变量。
4. 执行过的测试、Lint、类型检查、构建和结果。
5. 手工验收步骤和实际结果。
6. 未执行或失败的检查、已知问题和剩余风险。
7. 建议的 Git commit 信息。

P16 另外说明设计确认项；P22 区分技术评测、真实供应商调用和人工教学评审；P23 区分技术准入与校方批准；P24 记录真实周期、样本和证据来源。任何阶段都不能把尚未发生的人工或外部验收写成通过。
