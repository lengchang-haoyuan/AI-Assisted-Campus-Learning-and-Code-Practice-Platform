## 1. 直接使用方法

有仓库访问能力的 AI，可以直接接收下面这段话。执行其他阶段时，只替换其中的阶段编号。

```text
项目目录：C:\Users\Administrator\Desktop\毕业设计\ScholarHub。
请读取“开发相关文档/AI提示词/CR_严格代码审查整改方案与AI执行提示词.md”，按其中共同约束执行 CR1。
先完成 CR0 的现状核对、当前问题复现和最小设计，然后实施 CR1 必要修复及回归；CR0 不是额外等待确认的关卡。
保留已有未提交修改，不重建项目，不处理后续阶段，不自动提交、推送或发布。
如触发项目规定的高影响操作确认门槛，先完成可审查的复现、影响分析及最小方案，再等待必要确认；已有明确授权不重复询问。
完成后按文档要求给出实际修改、验证证据、未完成项和下一阶段交接，停在 CR1。
```

也可以把整份文档作为附件提供给 AI，并明确“执行 CR几”。没有指定阶段时，先完成 CR0 并汇报推荐的下一步，不自行执行所有阶段。没有源码访问能力时，AI 应明确列出缺少的源码，不根据本文件臆造补丁。

生成本方案并不等于授权执行全部修复；把上面的执行指令发给 AI 后，才进入相应阶段。各阶段完成后均停止，由用户选择下一阶段。

## 2. 共同执行约束

1. 先读取当前工作区的 AGENTS.md（如存在）、$stop-that-shit、$frontend-backend-code-standards 及与本阶段有关的现有报告。沿用 Vue 3、TypeScript、Pinia、FastAPI、Pydantic、SQLAlchemy、MySQL 和现有分层、错误语义、依赖及锁文件。
2. 以当前源码、Git 和实际复现为准。本文件中的路径是入口，不是僵硬的允许修改清单；只沿当前问题的可达调用链扩展。已修复的问题核对证据后标为不再复现，不重复实现。
3. 保护现有未提交工作；不得 reset、覆盖、清空、重建或批量格式化。先记录基线，结束时区分原有差异与本阶段差异。不因“以后可能有用”加入通用层、哈希、新依赖或额外后台设施。
4. 新增或升级依赖、改变公共 API、持久化格式、数据库结构、迁移历史、兼容性、构建测试配置或安全策略，按当前项目规则先说明事实、影响、可选方案和推荐，再取得所需确认。本文件推荐的行为不是对这些操作的预先批准。不要把普通局部实现选择都升级成确认请求。
5. 自动化复现先使用内存测试、现有 Fake Provider、可控 Promise 和 HTTP Mock。真实 MySQL 写入前必须确认本轮专用隔离数据库、目标连接和空库/已有测试数据状态；不得沿用历史库授权，不得退回业务库，不得为测试自动清空已有库。
6. 不调用真实收费模型，不读取或输出密钥、Token、密码、私人业务正文。模型请求捕获使用虚构数据；确认的是消息边界和流程，不是模型质量。
7. 为当前缺陷添加能在修复前失败、修复后通过的行为回归；复用现有测试体系，不新增测试框架。并发测试优先用事件屏障控制交错，不靠长时间 sleep。SQLite/Mock 通过不能当作 MySQL 锁与事务已经通过。
8. 先跑本阶段相关检查；涉及前端时运行已有类型检查与构建。仅运行项目已有的格式、Lint、静态和安全检查；未配置或未运行的检查如实记录，不为凑齐门禁安装工具。
9. 中文日志使用“开发相关文档/开发日志/开发操作日志.md”；阶段报告使用“开发相关文档/阶段报告/”。不自动提交、推送、发布，不顺手重做 UI、上线保障、Spark、AI 预算或其他 P/R/L 阶段。

## 5. CR1：工作流运行与编辑互斥，防止旧结果提交

### 可直接交给 AI 的阶段指令

```text
执行本方案 CR1，遵循共同约束并先完成 CR0；本阶段仅处理 F01。

读取 services/workflow.py、repositories/workflow.py、repositories/workflow_execution.py、workflow/engine.py、models/workflow.py、API/Schema，以及 test_workflow.py、test_workflow_engine.py 和相关 Context 测试。

先复现：有合法 Context 的自有工作流 version=V，启动 POST /api/v1/workflows/{id}/run，body 为 {"expected_version":V,"mode":"all"}。用 Fake Provider 暂停模型返回，在另一请求 PUT /api/v1/workflows/{id}/nodes/{node_id} 修改 config.instruction；观察版本与原运行最终状态。

最小设计与实施：
1. 梳理运行启动、整图替换、节点/边增删改、工作流删除、结果提交、失败回收的现有锁顺序和事务边界。所有执行图写入必须在数据库事务中重新检查活动运行，覆盖 API 旁路；不能只依赖 workflow.status、前端禁用或进程内锁。
2. 与 start_run 共用可串行化的数据库互斥边界。先加锁并重新读状态，再修改 ORM 对象，防止检查后竞态或 autoflush 提前写入；统一本次直接相关路径的锁顺序，避免编辑、Context 更新、complete_node 之间反向等待。
3. 活动运行期间拒绝节点、边、整图的全部写入及工作流删除，使用项目现有冲突语义；包括节点名称/坐标和同值整图保存，因为这些入口当前也会递增图版本。仅放行不递增图版本的工作流自身 name/description 元信息更新，先核对现有接口行为。
4. 通过已有 workflow.version 和运行时内部参数，在节点提交和运行结束前核对启动使用的执行版本。发现不一致时旧结果不得写 Context/AIResult，也不得伪造 completed，应按现有失败语义收敛到可重试终态。
5. 模型调用前后各用短事务，不能持数据库锁等待模型。优先不新增表、字段、哈希或持久化格式；如证据要求这些变化，先给方案并确认。

验收：
- Fake Provider 挂起时，整图替换、节点/边增删改及工作流删除均不能破坏活动运行；拒绝前后图与版本不变。
- 两个并发启动同一工作流的请求不能同时获得有效活动运行；原运行正常完成后编辑恢复。
- 即使绕过编辑门禁制造版本变化，旧结果提交仍被拒绝，错误、取消和失败路径不遗留永久 running。
- 所有权拒绝、合法完成、失败重试和已有过期运行恢复仍正常；不额外设计新的调度器。
- Mock 验证状态机；锁与事务交错在本轮已确认的隔离 MySQL 中用两个独立连接验证。未取得隔离环境则明确保留该项待验收。

先运行 test_workflow、test_workflow_engine 及因共享路径实际受影响的测试；写 CR1 报告并停止，不执行 CR2。
```

## 6. CR2：统一执行配置与依赖变化后的失效规则

```text
执行本方案 CR2，遵循共同约束并先完成 CR0；确认 CR1 的运行中修改保护仍有效。本阶段仅处理 F05。

读取 services/workflow.py、repositories/workflow.py、workflow/engine.py、ContextManager 和整图替换/单节点/单边 API，以及对应测试。

先复现：工作流 A→B→C 全部 success，PUT 修改 B 的 config.instruction，用最新版本以 mode=incomplete 运行；当前实现仍跳过旧结果，可能返回“无需要执行”的 409。

实施要求：
- 先列字段分类：instruction、problem、student_code、expected_output、node_type、上下文读写策略等有执行语义；name、坐标等为展示语义。依据实际引擎读取字段判断，不把所有 JSON 变化一律当作纯展示。
- 改变执行输入时，本节点及 DAG 后继 stale；边的新增、删除和端点变化使实际受影响目标及后继 stale。保留无关分支。
- 单资源接口与整图替换执行同一不变量，必要时小范围复用现有规则；不为此搭建通用图框架。
- 同值保存、名称和位置编辑不额外触发模型重算；工作流整体状态随有效失效变化更新。
- 历史 run/result 保留为历史证据，不重写成新配置下的产物；运行期间仍由 CR1 拒绝修改。

验收：修改 B 后仅 B/C 失效，incomplete 仅重新执行 B/C；节点类型、题目、代码与指令变化均覆盖；边增删/改端点及整图保存结果一致；无关分支、同值保存和位置编辑不触发重算；全部节点仍 success 且无变化时保留原有“无可执行节点”语义。

运行相关 workflow/context 单元与 API 回归，记录具体调用节点和 Fake Provider 调用次数。写 CR2 报告并停止。
```

## 7. CR3：模型实际读取边界与项目级 Context 失效

```text

读取 agents/base.py、workflow/engine.py、context/context_manager.py、context/context_schema.py、repositories/workflow_execution.py、services/project_context.py 及相关 Agent/Context/Workflow 测试。

A. 修复最终模型消息的读取白名单（F03）
- 最小复现：requirements_analysis 节点 config.context_reads=[]，捕获最终 Fake Provider messages；当前仍有项目全部 values，默认白名单外的 database 也被发送。

- 验收最终序列化的消息，而非只断言辅助函数：默认集合准确，空集合得到空 values，合法缩小生效，非法扩大调用次数为 0；合法输出仍能通过 Schema、版本和写权限校验。

B. 修复共享 Context 更新的项目级失效（F06）

- 真实值未变化不触发无关失效；同工作流按原 DAG 规则处理下游。其他项目、无关字段和无关分支保持原状。

- 与手动 Context 更新路径的边界保持一致；统一直接相关锁顺序，不能在现有反向锁顺序上简单追加项目锁。
- 验收 A 改 language 后 B 的读取节点及后继 stale，B 的 incomplete 真正重算；其他项目不受影响；并发旧结果受控失败；提交失败回滚时 Context 和失效状态一起回滚。

先跑 Agent/Context/Workflow 对应测试；真实锁与提交原子性仅在已确认隔离 MySQL 验证。分别记录 A、B 证据，写 CR3 报告并停止。
```

## 9. CR5：教学任务更新的空值边界

```text
执行本方案 CR5，遵循共同约束并先完成 CR0；本阶段只处理 F04。

读取 schemas/teaching.py、services/teaching.py、repositories/teaching.py、models/teaching.py、api/v1/teaching.py、对应前端编辑器及 test_teaching.py。

复现：教师 PATCH /api/v1/campus/assignments/{id}，草稿 body={"expected_revision":当前值,"learning_objectives":null}，另测 acceptance_criteria=null。观察 Schema、赋值、事务提交和响应 list(None) 的先后。
```
