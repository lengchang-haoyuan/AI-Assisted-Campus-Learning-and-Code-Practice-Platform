# P21 校园社区治理：可直接投喂给 AI 的提示词

基于现有校园社区、P17 角色与账号管理以及 P19 站内通知，为 `ScholarHub` 增加最小人工治理闭环。本阶段只做可管理的校园作品社区，不扩展泛社交功能。

## 先检查现状

读取工作区规则、前后端目录职责、AI 提示词 README、已确认的 P16 方案和相关报告。检查项目发布/撤回、社区列表与详情、评论、点赞、收藏、浏览统计、账号状态和管理操作记录。

先说明当前已发布项目和评论如何兼容治理状态。不得直接把历史内容全部通过、全部下架或删除；历史数据处理必须有审查方案与用户确认。

## 本阶段目标

- 实现作品发布申请、人工审核、通过、退回、撤回和下架，提供作者进度与管理员待处理列表；沿用 P16 已确认状态名称。
- 用户能够举报项目或评论，填写有界原因；管理员查看必要内容、处理并记录理由，用户能够获知与自己相关的处理结果并提交必要的复核申请。
- 复用 P17 的账号停用能力处理获授权的账号处罚，不另造一套身份系统；管理动作需要确认和审计。
- 发布时提供署名、来源或使用许可说明，以及 AI 辅助使用声明；声明不等于平台已自动验证版权或学术原创性。
- 教师可维护有明确来源和人工审阅记录的实践项目模板，模板也走已确认发布规则，不把 AI 随机生成内容冒充官方教学材料。

## 关键规则

1. 校园公开范围只向符合 P17 校园访问规则的用户开放；本阶段不自动开启匿名公网访问。
2. 待审、拒绝或下架内容在列表、详情、搜索/筛选、收藏入口及互动接口中遵守同一可见性规则；作者预览和管理员审核采用明确授权，不能只从列表隐藏。
3. 已通过内容被作者修改时，采用已确认的重新审核或公开快照方案，不能绕过审核即时替换公开内容。状态并发变更、重复审核和撤回需有一致性规则。
4. 管理员仅查看治理所需的发布或举报内容，不因此读取私人学习记录、项目 Context 或完整 AI 输入；举报者身份与内部备注不对无关用户公开。
5. 举报、评论与通知限制长度、数量和请求频率。复用 MySQL、当前审计和站内通知能力，不引入推荐算法、外部内容平台或大型消息队列。
6. 定义下架、恢复、删除与现有计数的关系，保留审查所需记录但不过度保留个人内容；不通过删数据修正统计。

## 执行要求

沿用 Vue 3 + TypeScript + Element Plus、FastAPI + SQLAlchemy + MySQL 与 Router → Service → Repository。遵循 `$frontend-backend-code-standards`，Schema 与 Models 分离；新增依赖、公共 API、数据库或持久化规则变更先说明风险、兼容方案并等待确认。

前端复用原社区和管理入口，API 集中在 `src/api`，类型明确；处理加载、空、失败、重试、重复提交与权限变化。审核动效保持克制，状态不能只靠颜色，支持键盘、窄屏和减少动态效果。

## 验收标准

- 作者申请发布 → 管理员通过 → 校园用户浏览互动 → 用户举报 → 管理员下架 → 作者收到原因并申请复核 → 处理结果可查询，全部来自真实数据库。
- API/Service 测试覆盖跨用户修改、伪造审核权限、重复举报或处理、并发撤回与审核、发布后修改、直连下架详情及收藏入口的访问限制。
- 既有社区互动与统计按新口径正确工作，原始用户内容和历史数据未被未授权批量处理。
- 不新增私信、关注、在线 IDE、复杂推荐或自动 AI 判罚；不得把模板准备完成当作教师已经认可。
