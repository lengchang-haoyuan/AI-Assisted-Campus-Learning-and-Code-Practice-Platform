# P17 校园身份与账号管理：可直接投喂给 AI 的提示词

基于现有认证、JWT 和已确认的 P16 方案，实现 `ScholarHub` 的校园身份、固定角色和账号管理。本阶段不实现班级教学、社区审核或学校统一登录。

## 先检查现状

读取工作区规则、项目说明、前后端目录职责、AI 提示词 README、P16 设计及确认记录。检查 User、AuthService、SecurityService、JWT 依赖、当前注册和滑块登录协议、用户 Store、路由守卫和认证测试。

先报告目录、依赖和兼容性影响。沿用 Vue 3 + TypeScript + Element Plus 与 FastAPI + SQLAlchemy + MySQL，不另建管理后台工程；遵守 Router → Service → Repository 分层。P16 未确认时，先说明差异并暂停受影响开发。

## 本阶段目标

- 实现学生、教师、管理员三个固定角色。普通注册不能选择角色；教师和管理员身份只能经受控流程授予，前端隐藏入口不能代替后端授权。
- 实现已确认的邀请入校流程：邀请有用途、有效期、使用次数和目标身份边界，不能通过改请求获得更高角色；并发兑换不能重复生效。
- 提供最小账号管理页面：有界查询账号、查看必要身份信息、启用和停用、受控角色调整，危险操作确认并记录操作者、对象、原因、时间和结果。
- 提供当前用户改密与身份核验后的安全重置。复用现有 Argon2/JWT；一次性凭证不得记录到日志、数据库明文或文档，不能由管理员查看用户原密码。
- 提供首个管理员的受控初始化方式：无内置账号密码，不将首个普通注册者自动提升为管理员；禁止静默提升历史用户，防止最后一个有效管理员被误停用或移除。

## 安全与兼容性

1. 账号停用、重置密码或角色撤销后，旧会话的行为必须明确并由服务端执行；不能等到前端刷新才撤销权限，也不能单纯信任旧 JWT 的角色声明。
2. 保留既有普通用户与私人数据，按 P16 明确“已注册”与“获准进入校园范围”的区别；改变注册、登录或 `/users/me` 契约前说明客户端和测试迁移方案。
3. 现有滑块只是基础验证，不能把它宣称为专业反机器人系统。邀请、登录、改密和重置需要适配单实例部署的有界防滥用策略，不以新增 Redis 为默认前提。
4. 管理员不默认获得私人学习记录、项目 Context、AI 敏感输入的读取权。审计记录不保存密码、完整认证头、重置链接或个人信息正文。
5. 按工作区规则使用 `$frontend-backend-code-standards`；新增依赖、公共 API、数据库或安全策略变更先说明并等待确认。迁移只做已批准的本阶段增量，Models 与 schema.sql 保持一致。

## 前端要求

API 集中在 `src/api`，TypeScript 不使用 `any` 或双重断言。沿用已有冷白、海沫绿、钴蓝设计和适量过渡反馈，不重新设计整个站点。账号切换和会话失效清理旧 Store，处理加载、空、失败、重复提交和权限变化；支持键盘、窄屏及减少动态效果。

## 验收标准

- 跑通受控初始化管理员 → 发放邀请 → 校园成员注册或加入 → 登录 → 获取本人身份 → 改密 → 旧会话按规则失效。
- API/Service 测试覆盖角色伪造、匿名访问、学生访问管理接口、失效邀请、并发兑换、重复账号、错误原密码、重置凭证重放、停用账号和最后管理员保护。
- 浏览器验证不同角色入口、失败反馈和退出后数据清理；管理操作记录存在但无秘密。现有注册/滑块/JWT 测试按已确认契约回归。
- 临时测试账号隔离且可清理；不得批量提升或重置已有账号来通过验收。
