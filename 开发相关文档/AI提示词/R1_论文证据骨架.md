# R1 论文证据骨架：可直接投喂给 AI 的提示词

现在执行 ScholarHub [毕业设计整改方案](../开发规划/20260927-毕业设计整改方案.md)中的 **R1**。先读取 R0 的范围页与任务书对照表、当前仓库规则、根 README、项目说明和相关代码。若 R0 尚未形成可用范围，先指出缺口；可以做只读证据盘点，但不要自行扩大或重定题目。

## 本步目标

1. 按 R0 主线整理学生项目实践、学习任务、AI 辅助、过程统计及必要教学反馈的需求。分别标注真实访谈或任务书来源、可核对文献来源、开发者提出的设计假设；没有真实用户材料就如实写“设计假设”。
2. 建立“需求 → 实现 → 验证”矩阵。逐项定位实际前端页面/API、后端 Router/Service/Repository、关键数据表、自动化测试或手工验收；找不到实现或验证的项目标为缺口，不凭 README 描述补造代码。
   将整改方案 C1–C4 标为待对应 R 阶段复现和收口的设计问题；C5 标为生产部署条件下的架构边界，不预写成毕业原型的已修复缺陷。
3. 提炼论文所需的总体架构图、一条核心流程时序图、关键实体关系图和个人/教学数据权限矩阵。图与文字以当前模型、Schema、接口和授权逻辑为准。
4. 记录单体架构、MySQL 统计、版本化 ProjectContext、Workflow 记录、提交版本冻结与权限隔离等关键设计取舍，每项说明需求、现有方案、替代方案及局限。
5. 形成论文目录与章节提纲、图表清单、参考文献台账。需要查找文献时给出可核对的作者、题名、年份和来源；不得编造引用、访谈、问卷或专家意见。学校格式不明时采用清楚的草稿结构并标记待套用模板。

## 交付与边界

- 将论文提纲、矩阵和图表清单放在 `开发相关文档/答辩材料/`，可复用根 README 的现有架构与 ER 图，但须核对代码后再引用。
- 本步做论文证据组织，不新增模块、迁移、依赖或页面，不生成没有来源支撑的研究结论。
- P22/P23/P24 的计划、技术检查、教师批准和真实试点必须分别标注，不能并入“已实现”。
- 只读取必要的代码和文档；发现主线阻断缺陷时记录位置与影响，交给 R2/R4 处理。

## 完成判据

- 每项核心需求均有实现位置和验证状态，允许状态为“待验证”，不能空缺后默认通过。
- 每张论文图可追溯到当前代码或明确标为概念图；论文提纲突出三个关键技术点，不逐页罗列系统。
- 按现有目录约定追加中文时间索引操作记录和本步报告。用中文汇报证据矩阵覆盖范围、找不到证据的主张、参考文献待补项和 R2/R3 可使用的输入；不要提交或推送 Git。
