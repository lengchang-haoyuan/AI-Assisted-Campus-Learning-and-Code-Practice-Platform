# R4 文档一致性与最终验证：可直接投喂给 AI 的提示词

现在执行 ScholarHub [毕业设计整改方案](../开发规划/20260927-毕业设计整改方案.md)中的 **R4**。先读取 R0–R3 已产生的范围页、矩阵、演示和实验结果；核对 Git 状态及当前仓库规则。若某步未完成，保留其未完成状态，不为使文档好看而补造验收。

## 本步目标

1. 对照当前代码与最新证据，统一根 README、项目说明、`PRODUCT.md`、知识网络进度入口及演示指南中的题目、阶段状态、演示数据和 AI/试点边界。历史阶段报告保留其当时日期与结论，需要时加当前入口说明，不全库重写。
2. 建立最终版本验证清单：后端已配置的测试、前端类型检查与构建、适用的浏览器回归、隔离 MySQL 主线演示。按相关性执行并记录完整命令、环境、时间、通过/失败；旧报告中的 203 项不自动算作本次通过。
3. 将问题分成“阻断答辩”“影响主线但可解释”“扩展模块”。只修复有复现证据且影响本次毕业交付的问题；不做无关重构、补齐整个 P22/P23 或追加新功能。
4. 为整改方案 C1–C4 建立逐项收口表，写明复现、处理决定、代码/文档变化、回归结果和未完成原因。C5 的同步长任务、进程内状态和前端本机回退按实际部署目标记录为局限或 P23 工作，不擅自重构任务执行架构。
5. 若必须修改公共 API、数据库结构/迁移、依赖、构建/测试/安全策略，先提供事实、风险、可行方案与推荐，取得确认后实施。不得删测试、关闭检查或放宽权限以换取通过。
6. 遵循工作区 `AGENTS.md`、`$stop-that-shit` 和 `$frontend-backend-code-standards`，更新中文时间索引操作记录和单次验证报告，保护用户未提交修改；只报告实际执行结果和剩余风险。

## 交付与验收

- 形成状态一致的项目入口、最终测试记录、问题清单和必要的最小修复证据。文档没有“已完成/仅设计/未开始”互相冲突的当前状态。
- C1–C4 没有无解释的悬空结论；各项检查分别标注通过、失败、未运行及原因。隔离演示、Fake Provider、真实模型和真实教师评价不混为一种证据。
- 最终中文汇报文件变化、关键决定、测试与构建结果、未执行项和进入 R5 的条件；不要提交或推送 Git，只给出 commit 建议。
