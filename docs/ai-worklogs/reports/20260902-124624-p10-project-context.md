## 需求摘要

在 P09 Workflow 基础上建立与 Project 关联的共享 ProjectContext，支持核心项目字段和 `architecture`、`features`、`constraints`、`extensions` 扩展字段，记录版本、UTC 更新时间、来源和逐字段元数据。节点必须按最小权限读取和写入 Context，并在依赖字段变化时标记自身或 DAG 下游节点 `stale`。本阶段不调用真实模型、不执行 Agent 或 Workflow。

- 新增所有权、版本冲突、字段白名单、JSON 安全边界、Project 核心字段漂移识别和统一错误映射。

## 关键设计决定

- 决定：复用 P01 的 `projects.context_data` JSON、P09 的 `workflow_nodes.context_version` 和 `stale`，不新增表或迁移。
- 原因：现有结构已完整覆盖 P10 的持久化需求，避免无必要数据库变更和字段漂移。
- 决定：Context 文档固定 `schema_version=1`，业务版本从 1 开始；有效变更递增一次，无变化不递增；更新使用 `expected_version` 和 Project 行锁防止覆盖并发修改。
- 决定：普通字段整体替换，可空字段以 `null` 清空；`architecture` 和 `extensions` 使用受限 JSON Merge Patch，嵌套 `null` 删除键。
- 决定：节点类型拥有固定默认读写白名单，`config.context_reads/context_writes` 只能缩小权限。字段改变后标记直接依赖节点和 DAG 下游；来源节点不因自身写入被标记 stale，但其下游失效。
- 决定：Context API 修改核心字段时在同一事务内同步 Project 列；旧 Project API 导致的字段漂移会被报告为 `is_stale`，节点在同步前拒绝读写。
- 用户确认：P10 提示词已明确授权新增上下文 API 和定义 `context_data` 持久化格式；未触发新增依赖或数据库结构确认门槛。

## 兼容性与安全影响

- 公共 API：仅新增 `/api/v1/projects/{project_id}/context` 与 `/api/v1/workflows/{workflow_id}/nodes/{node_id}/context/*`，不修改 P00-P09 已有请求和响应。
- 数据与迁移：不修改 `schema.sql`、SQLAlchemy Models、18 张表或迁移历史；首次创建前 `context_data` 保持 `NULL`。
- 权限：所有接口要求 JWT，Project 和 WorkflowNode 均在 Service 校验当前用户所有权；不能跨用户读取 Context。
- 输入：持久化数据、节点结果和外部 JSON 均经过 Pydantic Schema；顶层拒绝额外字段，JSON 限制 256 KiB、8 层和 100 项数组，并拒绝敏感键。
- 时间与秘密：所有 Context 时间必须带时区并归一为 UTC；未提交数据库凭据、JWT、密码、Token 或 AI Key。

## 剩余风险与后续建议

- 若客户端绕过 Context API，使用旧 Project API 修改核心字段，Context 会进入可检测的 stale 状态；客户端需要读取 `stale_fields` 并通过 Context 更新接口同步后，节点才能继续读写。
- 已存在但不符合 `schema_version=1` 的手工 JSON 会返回 409，不会被静默覆盖；当前真实 MySQL 验收未发现此类 P10 数据。
- P11/P12 应复用本阶段节点权限和 Context Service，不应直接读取 `projects.context_data` 或让模型返回值绕过 Schema。
